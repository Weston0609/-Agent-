## agent.rag.eval_ragas

# agent.rag.eval_ragas：用 RAGAS 评估 RAG 系统

> 一句话直觉：RAG（Retrieval-Augmented Generation，检索增强生成）系统“看起来能答”，但要看它**答得准不准、检索得对不对、有没有幻觉（hallucination）**，就需要一套自动化评估指标，RAGAS 就是做这件事的常用工具。

---

## 1. 为什么 RAG 需要专门评估？

RAG 系统通常由两部分组成：

1. **Retriever（检索器）**：从知识库中找出与问题相关的文档片段。
2. **Generator（生成器）**：基于问题和检索到的上下文，生成最终回答。

传统文本生成评估常用 BLEU、ROUGE 等，但它们主要看“字面重叠”，不适合 RAG，因为：

- 回答可以换一种说法仍然正确；
- 检索到的上下文可能很多，但只有一部分真正被用到；
- 模型可能编造上下文里没有的内容，即**幻觉（hallucination）**。

RAGAS（Retrieval Augmented Generation Assessment）提供了一组更贴近 RAG 的指标，例如：

- **Faithfulness（忠实度）**：回答是否完全由给定上下文支持；
- **Answer Relevancy（答案相关性）**：回答是否直接切题；
- **Context Precision（上下文精确率）**：检索到的上下文中，相关内容是否排在前面；
- **Context Recall（上下文召回率）**：标准答案所需信息是否都被检索到。

本节先建立最小可运行认知：用 RAGAS 对一组“问题-回答-上下文-标准答案”做评估。

---

## 2. RAGAS 的输入数据长什么样？

RAGAS 通常接收一个数据集，每条样本至少包含这些字段：

- `question`：用户问题；
- `answer`：RAG 系统生成的回答；
- `contexts`：检索器返回的上下文列表；
- `ground_truth`：人工标注的标准答案，也叫 reference。

可以把它理解成一张表：

| question | answer | contexts | ground_truth |
|---|---|---|---|
| 什么是 RAG？ | RAG 是检索增强生成…… | ["RAG 是...", "检索增强..."] | RAG 是结合检索与生成的方案 |

RAGAS 会调用 LLM（Large Language Model，大语言模型）和 Embedding（嵌入）模型来打分，因此你需要配置模型。

## 4. 指标怎么读？

运行后你会得到类似：

```text
faithfulness: 0.85
answer_relevancy: 0.92
context_precision: 0.78
context_recall: 0.80
```

解释：

- **faithfulness 低**：回答可能包含上下文没有依据的内容，优先检查生成 prompt 是否要求“只依据上下文回答”。
- **answer_relevancy 低**：回答可能跑题，检查问题理解和回答格式。
- **context_precision 低**：检索结果里噪声多，考虑改进 chunking（分块）、rerank（重排）或向量库。
- **context_recall 低**：需要的信息没被检索到，考虑增加召回数量、改 embedding 模型或补知识库。

---

## 5. 工程中怎么接入？

建议把 RAGAS 评估做成流水线的一步：

1. 准备一批真实问题；
2. 跑 RAG 系统，记录 `answer` 和 `contexts`；
3. 人工补 `ground_truth`；
4. 用 RAGAS 批量打分；
5. 把分数纳入回归测试，防止改 prompt 或换模型后指标下降。

注意：RAGAS 很多指标依赖 LLM 打分，所以评估本身有成本，也会受评估模型能力影响。工程上要固定评估模型版本，并保留样本集版本。

## agent.rag.hallucination_guard

# 幻觉护栏（Hallucination Guard）：给 RAG 代理系上安全带

> **一句话直觉**：检索增强生成（RAG, Retrieval-Augmented Generation）里的“幻觉护栏（Hallucination Guard）”，就是当模型想瞎编时，能把它按回证据上，并告诉你“这句话到底有没有出处”。

## 1. 为什么需要幻觉护栏

大语言模型（LLM, Large Language Model）本质是**下一个词概率预测器**，它追求“像人话”，而不是“说真话”。在 RAG（Retrieval-Augmented Generation，检索增强生成）里，我们虽然把外部文档塞进了上下文（Context），但模型仍可能：

- 忽略检索内容，凭记忆回答；
- 把不同文档的片段“缝合”成看似合理的事实；
- 引用不存在的页码、链接、法规条款。

幻觉护栏不是让模型“变聪明”，而是加一道**可验证的防线**：

- 生成后，把回答拆成“原子声明（atomic claim）”；
- 对每个声明，回到检索证据中找支持；
- 没有证据支持的声明，要么删除，要么标记为“未经验证”。

下面用 5 个小节逐步实现一个最小可用的护栏。

---

## 2. 最小闭环：答案 + 证据 + 校验

先不引入复杂模型，只用字符串匹配理解护栏骨架。

```python
# 第1步：模拟检索到的证据（真实系统中来自向量库）
docs = [
    "RAG 是检索增强生成，先检索再生成。",
    "幻觉护栏的目标是减少没有依据的陈述。",
    "温度参数 temperature 越高，输出越随机。",
]

# 第2步：模拟模型生成的答案（包含一句幻觉）
answer = "RAG 是检索增强生成，幻觉护栏能完全消除幻觉，温度越高输出越随机。"

# 第3步：把答案拆成原子声明（这里用逗号、句号粗切）
import re
claims = [c.strip() for c in re.split(r"[，。；;]", answer) if c.strip()]

# 第4步：逐条检查是否有证据支持（最简单的子串包含判定）
def supported(claim: str, docs: list[str]) -> bool:
    # 只要某个文档包含该声明的关键片段，就认为有支持
    # 工程中应换成嵌入相似度或 NLI（自然语言推理）模型
    return any(claim in d or d in claim for d in docs)

for c in claims:
    print("✓" if supported(c, docs) else "✗ 无依据", c)
```

**结论**：护栏的第一性原理是“逐声明验证”，而不是整体看答案像不像。

---

## 3. 关键升级：从“字符串匹配”到“语义支持”

字符串匹配会漏掉“同义改写”。工程中常用两种做法：

1. **嵌入相似度（Embedding Similarity）**：把声明和证据编码成向量，算余弦相似度。
2. **自然语言推理（NLI, Natural Language Inference）**：判断证据是否“蕴含（entail）”声明。

下面用 `sentence-transformers` 演示嵌入方案（本地可装：`pip install sentence-transformers`）。

```python
from sentence_transformers import SentenceTransformer, util

# 用一个小型多语言模型，CPU 也能跑
model = SentenceTransformer("paraphrase-multilingual-MiniLM-L12-v2")

def best_support(claim: str, docs: list[str], threshold: float = 0.6):
    # 把声明和所有证据编码成向量
    emb_claim = model.encode(claim, convert_to_tensor=True)
    emb_docs = model.encode(docs, convert_to_tensor=True)
    # 计算与每条证据的余弦相似度
    scores = util.cos_sim(emb_claim, emb_docs)[0]
    best_idx = int(scores.argmax())
    return float(scores[best_idx]), docs[best_idx]

claim = "幻觉护栏能减少没有依据的陈述"
score, evidence = best_support(claim, docs)
print(f"相似度={score:.3f}，最相关证据：{evidence}")
print("判定：", "有支持" if score >= 0.6 else "无支持")
```

**结论**：阈值 `threshold` 是护栏的“灵敏度旋钮”。太低会放过幻觉，太高会把正确改写误杀。

---

## 4. 工程化护栏：三种处置策略

验证之后，要决定怎么处置“无依据”的声明。常见三类策略：

| 策略 | 行为 | 适用场景 |
|---|---|---|
| 删除（prune） | 直接删掉无依据句子 | 客服、医疗等高风险 |
| 标注（annotate） | 保留但加“未经验证”标记 | 研究辅助、探索性问答 |
| 重写（rewrite） | 让模型只保留有依据部分 | 需要自然语言的对外回答 |

```python
def guard(answer: str, docs: list[str], threshold: float = 0.6, mode: str = "annotate"):
    claims = [c.strip() for c in re.split(r"[，。；;]", answer) if c.strip()]
    kept = []
    for c in claims:
        score, _ = best_support(c, docs, threshold)
        if score >= threshold:
            kept.append(c)
        elif mode == "prune":
            continue
        elif mode == "annotate":
            kept.append(f"{c}（未经验证）")
        elif mode == "rewrite":
            kept.append("[已省略无依据内容]")
    return "，".join(kept)

print(guard(answer, docs, mode="annotate"))
print(guard(answer, docs, mode="prune"))
```

**结论**：护栏不是单一开关，而是一组可配置策略，应根据业务风险选择。

---

## 5. 常见误区与选型建议

- **误区一：护栏能“完全消除”幻觉。** 不能。它只能减少并暴露幻觉，不能保证真理。
- **误区二：只看答案整体相似度。** 必须逐声明验证，否则一句真话会“掩护”一句假话。
- **误区三：阈值一刀切。** 不同领域、不同问题类型应分档调参，并用标注集评估。
- **选型建议**：
  - 原型阶段：字符串/嵌入相似度 + `annotate`。
  - 生产阶段：NLI 模型 + 引用溯源（citation grounding）+ 人工抽检。
  - 高风险场景：强制 `prune`，并让模型输出证据 ID。

> 记住这句工程口诀：**先检索、再生成、后验证；无证据、不输出、要标注。**
