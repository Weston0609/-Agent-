## py.async.backpressure

# py.async.backpressure：异步世界里的"限流器"

## 一句话直觉

> **背压（Backpressure）** 就是让"生产数据的速度"被"消费数据的速度"限制住，防止内存被无限堆积的任务撑爆。

想象一家奶茶店：前面来了 100 个顾客不停点单，后厨只有 2 个员工做奶茶。如果没有背压，收银台会一直接把订单"甩"进后厨，桌子堆满订单纸，最后连走路的地方都没有。有了背压，收银台最多只允许 10 张订单在"等待区"，满了就暂停接单——这就是背压的意义。

---

## 1. 为什么需要背压：生产者-消费者速度不匹配

在 `asyncio` 里，最常见的场景是：一个协程（coroutine）不停地产生数据（生产者，producer），另一个协程慢悠悠地处理（消费者，consumer）。如果完全没有限制，生产者会瞬间把队列塞满，内存爆炸。

```python
import asyncio

async def producer(q: asyncio.Queue):
    # 没有背压：疯狂生产，永不等待
    i = 0
    while i < 1_000_000:
        q.put_nowait(i)   # 从不 await，队列无限增长
        i += 1

async def consumer(q: asyncio.Queue):
    while True:
        item = await q.get()
        await asyncio.sleep(0.001)  # 假装处理很慢

async def main():
    q = asyncio.Queue()  # 无界队列，危险
    await asyncio.gather(producer(q), consumer(q))

# asyncio.run(main())  # 会很快吃光内存
```

**结论**：无界队列（unbounded queue）在异步代码里等同于"把炸弹埋在内存里"。

---

## 2. 核心武器：`asyncio.Queue(maxsize=N)`

解决方式非常直接——给队列设一个上限 `maxsize`。当队列满时，`await q.put(item)` 会**自动挂起生产者协程**，直到消费者腾出空位。这就是最基础的背压机制。

```python
import asyncio

async def producer(q: asyncio.Queue):
    for i in range(10):
        await q.put(i)          # 队列满时会阻塞在这里
        print(f"[P] 放入 {i}, 队列大小={q.qsize()}")
    await q.put(None)           # 哨兵，通知消费者结束

async def consumer(q: asyncio.Queue):
    while True:
        item = await q.get()
        if item is None:
            break
        await asyncio.sleep(0.2)  # 消费慢
        print(f"    [C] 取出 {item}")
        q.task_done()

async def main():
    q = asyncio.Queue(maxsize=3)  # ★ 关键：容量 3，形成背压
    await asyncio.gather(producer(q), consumer(q))

asyncio.run(main())
```

**观察输出**：生产者永远不会比消费者"领先超过 3 个"。这就是背压在做工。

## 3. `task_done()` 与 `join()`：什么时候整批处理完毕？

光有 `maxsize` 还不够，工程里经常还要知道"所有任务都被处理完了"。`asyncio.Queue` 提供了一对 API：

- `q.task_done()`：消费者说"我刚取的那条我处理完了"。
- `await q.join()`：一直等到队列里所有被取走的任务都被 `task_done()` 标记为止。

```python
import asyncio

async def worker(q: asyncio.Queue, name: str):
    while True:
        item = await q.get()
        if item is None:
            q.task_done()
            return
        await asyncio.sleep(0.1)
        print(f"worker-{name} 处理完 {item}")
        q.task_done()

async def main():
    q: asyncio.Queue = asyncio.Queue(maxsize=5)
    workers = [asyncio.create_task(worker(q, str(i))) for i in range(3)]

    for i in range(20):
        await q.put(i)          # 队列满时自动等待

    await q.join()              # 阻塞直到所有任务被消费并 task_done
    print("全部处理完毕")

    for _ in workers:
        await q.put(None)       # 通知 worker 退出
    await asyncio.gather(*workers)

asyncio.run(main())
```

**工程要点**：`q.join()` 是判断"批处理结束"的标准做法，比手动计数器可靠。

## 4. 更高级的背压：Stream 层与信号量

### 4.1 网络 Stream 的 `write` 与 `drain`

`asyncio` 的 `StreamWriter` 内部也有缓冲区。写入太快、对端读得太慢时，缓冲区会积压。此时 `await writer.drain()` 就是"等待直到可以继续写"的背压接口。

```python
import asyncio

async def handle(reader: asyncio.StreamReader, writer: asyncio.StreamWriter):
    for i in range(1000):
        writer.write(f"line {i}\n".encode())
        await writer.drain()   # ★ 背压：写太急就挂起
    writer.close()
    await writer.wait_closed()

async def main():
    server = await asyncio.start_server(handle, "127.0.0.1", 8888)
    async with server:
        await server.serve_forever()

# asyncio.run(main())
```

### 4.2 `asyncio.Semaphore`：自定义并发上限

当你不是在做"生产者-消费者"，而是想"同时对下游发起不超过 N 个请求"时，信号量（semaphore）就是最直接的背压工具。

```python
import asyncio

async def fetch(sem: asyncio.Semaphore, i: int):
    async with sem:                # 最多允许 3 个并发
        print(f"开始 {i}")
        await asyncio.sleep(0.5)
        print(f"结束 {i}")

async def main():
    sem = asyncio.Semaphore(3)
    await asyncio.gather(*(fetch(sem, i) for i in range(10)))

asyncio.run(main())
```

## 5. 总结：什么时候用哪种背压

| 场景 | 推荐工具 |
|------|----------|
| 生产者-消费者，内部任务分发 | `asyncio.Queue(maxsize=N)` + `task_done()`/`join()` |
| 网络收发，防止写缓冲爆炸 | `StreamWriter.drain()` |
| 限制对下游的并发请求数 | `asyncio.Semaphore(N)` |
| 想丢弃"过老"数据只保留最新 | `asyncio.Queue(maxsize=1)` + 取出前清空 |

**一句话记住**：背压不是"减少并发"，而是"让快的一方等一等慢的一方"——保证系统在过载时**优雅地降速**，而不是崩溃。

## 动手练习

**任务**：写一个异步"图片抓取模拟器"。

要求：
1. 一个生产者协程，每 0.05 秒生成一个"图片编号"（共 50 个），放入 `asyncio.Queue(maxsize=5)`。
2. 两个消费者协程（worker），从队列里取编号，用 `asyncio.sleep(random.uniform(0.1, 0.3))` 模拟下载，打印 `worker-X: 下载图片 i 完成`。
3. 使用 `q.join()` 等待全部下载完毕后再打印 `全部完成`。
4. 用 `time.perf_counter()` 统计总耗时，并试着把 `maxsize` 改成 1、50，观察耗时变化并解释原因。

**验收标准**：程序结束时队列为空，所有 50 张图片都被处理，且能说清"扩容 maxsize 为什么不一定更快"。

```python
import asyncio
import random
import time

async def producer(q: asyncio.Queue):
    for i in range(50):
        await q.put(i)                     # 队列满时自动挂起（背压生效）
        await asyncio.sleep(0.05)

async def worker(q: asyncio.Queue, name: str):
    while True:
        item = await q.get()
        if item is None:
            q.task_done()
            return
        await asyncio.sleep(random.uniform(0.1, 0.3))
        print(f"worker-{name}: 下载图片 {item} 完成")
        q.task_done()

async def main():
    q: asyncio.Queue = asyncio.Queue(maxsize=5)
    workers = [asyncio.create_task(worker(q, str(i))) for i in range(2)]

    t0 = time.perf_counter()
    await producer(q)
    await q.join()                          # 等待所有任务 task_done
    elapsed = time.perf_counter() - t0
    print(f"全部完成，耗时 {elapsed:.2f}s")

    for _ in workers:
        await q.put(None)
    await asyncio.gather(*workers)

asyncio.run(main())
```

## py.async.rate_limit

# py.async.rate_limit：异步限流完全入门

> 一句话直觉：当你用 `asyncio` 并发请求 1000 个网页、调用 1000 次 API 时，服务器或第三方接口往往有「每秒最多 N 次」的硬限制——限流（rate limiting）就是让你「跑得快，但不越界」的那道闸门。

前置知识：本讲假设你已能写基本的 `async def` / `await` 协程（coroutine），并知道 `asyncio.run()` 怎么启动事件循环（event loop）。如果还不熟悉，先看一眼官方 asyncio 的 Hello World 即可。

---

## 1. 为什么需要限流：并发会「压垮」对端

`asyncio` 的价值在于「IO 等待时切换去干别的活」。可一旦你把 10 万个请求同时 `gather` 出去，对端服务器会瞬间收到海量连接。轻则返回 429（Too Many Requests），重则把你 IP 封禁。

限流的目标不是「变慢」，而是**把并发速率控制在对端允许的范围内，仍保持高吞吐**。

下面是最朴素的「不限流」写法，先看它的威力（本地模拟 API）：

```python
import asyncio
import time

async def call_api(i: int) -> int:
    # 模拟一次 0.1 秒的网络请求
    await asyncio.sleep(0.1)
    return i

async def main():
    start = time.perf_counter()
    # 100 个请求全部同时发出
    results = await asyncio.gather(*(call_api(i) for i in range(100)))
    elapsed = time.perf_counter() - start
    print(f"完成 {len(results)} 个请求，耗时 {elapsed:.2f}s")

asyncio.run(main())
```

运行后你会看到约 0.1 秒就完成了——因为在等待时全部并发。但如果对端每秒只允许 5 次，这就直接违规了。

---

## 2. 方案一：Semaphore（信号量）控制并发数

`asyncio.Semaphore(n)` 是最简单、最常用的手段：同一时刻最多只有 n 个协程能进入临界区。它不是严格意义上的「每秒 N 次」，而是「同时 N 个」——这叫**并发限制（concurrency limit）**。

```python
import asyncio
import time

async def call_api(i: int, sem: asyncio.Semaphore) -> int:
    async with sem:                # 进入临界区，占用一个名额
        await asyncio.sleep(0.1)   # 模拟网络请求
        return i

async def main():
    sem = asyncio.Semaphore(5)     # 同时最多 5 个请求
    start = time.perf_counter()
    results = await asyncio.gather(*(call_api(i, sem) for i in range(100)))
    elapsed = time.perf_counter() - start
    print(f"完成 {len(results)} 个，耗时 {elapsed:.2f}s")

asyncio.run(main())
```

**直觉公式**：如果每个请求耗时 t 秒，并发为 n，则总耗时约为 `总请求数 / n * t`。上例 100 个请求、并发 5、每个 0.1s：约 2 秒左右完成。

适用场景：对端限制的是「同时在线的连接数」，比如数据库连接池、爬虫的并发上限。

---

## 3. 方案二：令牌桶（Token Bucket）实现「每秒 N 次」

很多 API 的限制是「每秒最多 N 次（RPS，Requests Per Second）」，对短突发（burst）也敏感。这时 Semaphore 不够——因为它只约束同时并发，不约束速率。

**令牌桶算法**：想象一个桶，容量为 `capacity`，以每秒 `rate` 个的速度往桶里放令牌。请求需要先从桶里取一个令牌，取不到就等。

下面是一个最小可用的异步令牌桶：

```python
import asyncio
import time

class TokenBucket:
    """异步令牌桶：每秒补充 rate 个令牌，桶容量 capacity。"""
    def __init__(self, rate: float, capacity: float):
        self.rate = rate                 # 每秒补充的令牌数
        self.capacity = capacity         # 桶容量（应对突发）
        self.tokens = capacity           # 当前令牌数
        self.updated = time.monotonic()  # 上次补充时间
        self.lock = asyncio.Lock()       # 保护状态，避免竞态

    async def acquire(self) -> None:
        async with self.lock:
            while True:
                now = time.monotonic()
                # 按经过的时间补充令牌，但不超过容量
                elapsed = now - self.updated
                self.tokens = min(self.capacity,
                                  self.tokens + elapsed * self.rate)
                self.updated = now

                if self.tokens >= 1:
                    self.tokens -= 1
                    return
                # 令牌不足，计算需要等多久
                wait = (1 - self.tokens) / self.rate
                await asyncio.sleep(wait)
```

使用示例：

```python
async def worker(i: int, bucket: TokenBucket) -> int:
    await bucket.acquire()
    return i

async def main():
    bucket = TokenBucket(rate=5, capacity=5)   # 每秒 5 次，突发上限 5
    start = time.perf_counter()
    await asyncio.gather(*(worker(i, bucket) for i in range(20)))
    elapsed = time.perf_counter() - start
    print(f"20 个请求耗时 {elapsed:.2f}s（理论 ≈ {(20-5)/5:.1f}s + 首次突发）")

asyncio.run(main())
```

**关键点**：`asyncio.Lock` 保证「补充 + 检查 + 扣减」是原子操作；`await asyncio.sleep` 让出控制权，其他协程得以继续，不会阻塞整个事件循环。

## 4. 方案三：固定窗口（Fixed Window）——简单但有边界问题

如果只想限制「每 N 秒内最多 M 次」，可以每秒/每窗口检查计数。写法最简，但窗口切换处可能出现 2 倍突发（边界问题）。工程上更推荐令牌桶或滑动窗口（sliding window）。这里写一个仅供理解：

```python
import asyncio
import time

class FixedWindowLimiter:
    def __init__(self, max_calls: int, window: float = 1.0):
        self.max_calls = max_calls
        self.window = window
        self.count = 0
        self.window_start = time.monotonic()
        self.lock = asyncio.Lock()

    async def acquire(self) -> None:
        async with self.lock:
            now = time.monotonic()
            if now - self.window_start >= self.window:
                # 进入新窗口，重置
                self.window_start = now
                self.count = 0
            if self.count < self.max_calls:
                self.count += 1
                return
            # 本窗口已满，等到下一个窗口
            wait = self.window - (now - self.window_start)
            await asyncio.sleep(wait)
```

**什么时候用哪种**：
- 需要「同时并发 ≤ N」→ `Semaphore`。
- 需要「速率 ≤ N/s」→ `TokenBucket`。
- 需要「每固定窗口 ≤ N」→ 固定/滑动窗口。

---

## 5. 工程化：把限流封装成装饰器

零基础到工程级的关键差别是「能否复用」。把令牌桶写成装饰器，一行接入任何异步函数：

```python
import asyncio
import functools

def rate_limit(rate: float, capacity: float):
    """异步限流装饰器：每秒最多 rate 次，突发上限 capacity。"""
    bucket = TokenBucket(rate=rate, capacity=capacity)

    def decorator(func):
        @functools.wraps(func)
        async def wrapper(*args, **kwargs):
            await bucket.acquire()
            return await func(*args, **kwargs)
        return wrapper
    return decorator

# 使用
@rate_limit(rate=2, capacity=2)
async def call_remote(i: int):
    await asyncio.sleep(0.05)
    return i
```

**工程注意点**：
- 每个需要独立速率的目标用各自的 bucket（例如不同域名各自限流）。
- 在微服务/爬虫中，通常配合 `aiohttp`、`httpx.AsyncClient` 使用。
- 生产级更复杂的场景可参考 `aiolimiter` 库，它就是令牌桶的成熟实现。

## 小结表

| 方案 | 约束 | 是否有突发 | 复杂度 |
|------|------|-----------|--------|
| Semaphore | 同时并发数 | 无 | ★ |
| TokenBucket | 平均速率 | 有（≤容量） | ★★ |
| FixedWindow | 每窗口次数 | 边界可能 2 倍 | ★ |
| 滑动窗口 | 平均速率，无边界问题 | 无 | ★★★ |

核心心法：**限流是为了保护对方，同时也是为了保护你自己不被封禁**。选择哪种算法由对端的限制语义决定，不是越复杂越好。

## 本课题目

### single_choice · None



- [A] 队列会自动丢弃旧元素，内存保持稳定
- [B] 队列会无限增长，内存占用持续上升，甚至导致程序崩溃
- [C] put_nowait 会自动切换为阻塞等待，从而自然限速
- [D] 事件循环会检测到不平衡并暂停生产者任务

**参考答案**：1

**解析**：put_nowait 不会等待，队列无上界时元素不断堆积，会造成内存膨胀。它不会自动丢弃、不会自动阻塞，事件循环也不会自动暂停生产者。

### single_choice · None



- [A] 把队列的 maxsize 设置为一个有限值，并让生产者在 put 时等待
- [B] 把所有 put_nowait 改成多次重试
- [C] 把消费者改为同步函数
- [D] 在事件循环中手动调用 gc.collect()

**参考答案**：0

**解析**：有界队列配合 await queue.put() 会在队列满时挂起生产者，从而把压力反馈给上游，这是 asyncio 中常见的背压手段。

### single_choice · None



- [A] 在解析协程和写入协程之间使用有界队列，并让解析协程 await put
- [B] 在解析协程内部加 asyncio.sleep(0)
- [C] 在写入协程内部使用无限循环重试
- [D] 把队列容量设为 0，表示无限制

**参考答案**：0

**解析**：在速率不匹配的边界处引入有界队列并等待写入空间，是标准背压做法。sleep(0) 不限制速率，maxsize=0 表示无界。

### single_choice · None



- [A] 队列容量为零，任何 put 都会抛异常
- [B] 队列无界，put 永远不会因为满而等待
- [C] 队列容量为 1
- [D] 该写法在 asyncio 中非法

**参考答案**：1

**解析**：maxsize=0 是默认值，表示无界队列。它不会抛异常，也不是容量 1，写法合法。

### single_choice · None



- [A] 被挂起，事件循环可以去执行其他任务
- [B] 被终止，需要重新创建任务
- [C] 阻塞整个事件循环直到有空位
- [D] 进入忙等待，不断轮询队列
