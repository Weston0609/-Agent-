## agent.llm.prompt_engineering

# 智能体提示工程（Prompt Engineering）

> 一句话直觉：**提示工程就是用自然语言给大模型写“函数签名 + 少量示例”，让同一个模型在不改参数的情况下完成不同任务。**

你之前学过 GPT 架构、注意力、Tokenizer、SFT/RLHF、LoRA、vLLM 等，那些是“模型内部”。提示工程是“模型外部”的接口设计——不训练、不微调，只改输入。它是智能体（Agent）最便宜、最快、最可控的抓手。

---

## 1. 为什么提示工程成立：条件概率视角

大模型本质是一个自回归条件概率模型：

$$P(x_t \mid x_{<t})$$

你给的提示（prompt）就是条件 $x_{<t}$。改变提示 = 改变条件分布 = 改变输出。这就是提示工程的全部数学基础。

**关键结论：** 提示不是在“命令”模型，而是在**缩小下一个 token 的概率分布**。

```python
# 直觉演示：同一个模型，不同前缀 → 不同下一个 token 概率
# 伪代码，展示概念
prompt_a = "今天天气很"      # 后续大概率是“好/差”
prompt_b = "请用 JSON 输出天气："  # 后续大概率是 '{'
# 同一个 GPT，P(next_token | prompt) 完全不同
```

---

## 2. 提示的四个基本要素：角色、任务、上下文、格式

一个好提示通常包含四块：

| 要素 | 英文 | 作用 |
|---|---|---|
| 角色 | Role / Persona | 设定模型“是谁” |
| 任务 | Task / Instruction | 明确要做什么 |
| 上下文 | Context | 提供背景、数据、约束 |
| 输出格式 | Output Format | 规定返回结构 |

```python
# 四要素模板
def build_prompt(role, task, context, fmt):
    return f"""# 角色
{role}

# 任务
{task}

# 上下文
{context}

# 输出格式
{fmt}
"""

p = build_prompt(
    role="你是一名严谨的中文文本分类器",
    task="判断下面评论的情感倾向",
    context="评论：这家店的面很好吃，但服务太慢了。",
    fmt='只输出 JSON：{"sentiment": "正面|负面|中性", "reason": "..."}'
)
print(p)
```

## 3. 少样本提示（Few-shot Prompting）：用示例代替微调

零样本（zero-shot）只给指令；少样本（few-shot）给 2~5 个“输入→输出”示例，让模型**在上下文里做隐式学习**（in-context learning）。

**关键结论：** 示例的质量 > 数量。示例要覆盖边界情况、格式一致、标签正确。

```python
few_shot = """判断情感，只输出 正面/负面/中性。

评论：服务很好 → 正面
评论：太差了 → 负面
评论：还行吧 → 中性
评论：面好吃但服务慢 → """

# 模型会模仿上面的格式，输出“中性”或“混合”类判断
print(few_shot)
```

---

## 4. 思维链（Chain-of-Thought, CoT）：让模型先推理再作答

对需要多步推理的任务，直接问答案容易错。加上“请一步一步思考”能显著提升准确率——因为模型把中间步骤写进了上下文，相当于**外置了工作记忆**。

**关键结论：** CoT 对推理类任务有效，对事实检索类任务帮助有限，且会消耗更多 token。

```python
cot_prompt = """问题：小明有 12 个苹果，给了小红 1/3，又买了 5 个，现在有几个？

请一步一步计算，最后一行输出“答案：X”。
"""
# 模型会输出：12 的 1/3 是 4，剩下 8，加 5 = 13 → 答案：13
print(cot_prompt)
```

---

## 5. 结构化输出与智能体提示：JSON、工具调用、ReAct

智能体（Agent）需要模型输出**可被程序解析**的内容，于是：

- **结构化输出（Structured Output）**：强制 JSON / XML。
- **工具调用（Tool Calling / Function Calling）**：模型输出函数名+参数。
- **ReAct 模式**：Thought → Action → Observation 循环。

**关键结论：** 智能体提示的核心是**把自然语言输出约束成程序可执行的指令**。

```python
react_system = """你可以使用以下工具：
- search(query): 搜索
- calc(expr): 计算

请严格按格式输出：
Thought: 你的思考
Action: 工具名(参数)
Observation: 工具返回
... 循环直到得出 Final Answer。
"""
print(react_system)
```

要求：

2. 提示中包含四要素：角色、任务、上下文、输出格式。
3. 输出必须是 JSON，字段：`sentiment`（正面/负面/中性）、`aspects`（列表，如 ["口味","服务"]）、`summary`（一句话）。
4. 先写 zero-shot 版，再写 few-shot 版（给 2 个示例），对比输出稳定性。

**加分：** 改成 ReAct 风格，让模型先判断是否需要调用“翻译工具”。

```python
import json

# 一个最小的提示模板 + 解析器（可配合 Ollama / OpenAI API 使用）

def build_prompt(review: str) -> str:
    return f"""# 角色
你是一名严谨的中文评论分析器。

# 任务
从评论中提取情感、方面和摘要。

# 上下文
评论：{review}

# 输出格式
只输出 JSON，不要任何解释：
{{"sentiment": "正面|负面|中性", "aspects": ["..."], "summary": "..."}}
"""

def parse_output(text: str) -> dict:
    # 容错：去掉可能的 markdown 代码块
    text = text.strip().removeprefix("```json").removeprefix("```").removesuffix("```").strip()
    return json.loads(text)

# 模拟模型输出（真实场景替换为 API 调用）
fake_model_output = '{"sentiment": "中性", "aspects": ["口味", "服务"], "summary": "口味好但服务慢"}'

prompt = build_prompt("这家店的面很好吃，但服务太慢了。")
print("=== Prompt ===")
print(prompt)
print("=== Parsed ===")
print(parse_output(fake_model_output))
```

## agent.llm.few_shot

# 少样本提示（Few-Shot Prompting）：让大模型学会“照葫芦画瓢”

> **一句话直觉**：不训练、不调参，只在提示词（prompt）里塞几个“输入→输出”样例，就能把大模型（LLM, Large Language Model）快速“教”成你想要的样子。

---

## 1. 为什么需要 Few-Shot？——从零样本说起

大模型默认使用**零样本提示（Zero-Shot Prompting）**：只给任务描述，不给样例。

```python
# 零样本：直接问
prompt = "把下面的句子分类为『正面』或『负面』：这家餐厅的服务太慢了。"
# 模型可能输出：这句话表达了对服务速度的不满，属于负面。
```

问题：输出格式**不可控**，可能是解释、可能是中英混杂、可能多一句废话。

**少样本提示**的思路：给模型看几个“标准答案”，它会模仿格式和判断标准。

---

## 2. 一个样例 vs 多个样例：One-Shot 与 Few-Shot

- **单样本提示（One-Shot Prompting）**：1 个示例。
- **少样本提示（Few-Shot Prompting）**：2~5 个示例（经验值，通常不超过 10 个）。

```python
# 少样本示例：情绪分类
prompt = """判断下面评论的情感，只输出『正面』或『负面』。

评论：这家店味道很好。
情感：正面

评论：等了一个小时才上菜。
情感：负面

评论：环境一般，但服务员很热情。
情感："""
# 模型大概率输出：正面
```

**关键结论**：示例数量不是越多越好。2~5 个**覆盖典型情况**的示例，效果通常优于 20 个重复样例。

---

## 3. 少样本的三大要素：输入、输出、分隔

一个高质量少样本提示包含：

1. **任务说明**（Instruction）：要模型做什么。
2. **示例对**（Example Pairs）：`输入 → 输出`，格式一致。
3. **待预测输入**（Query）：放在最后，让模型续写。

```python
# 结构化模板
template = """任务：{instruction}

{examples}

输入：{query}
输出："""

examples = """输入：我喜欢这个产品
输出：正面

输入：质量很差，退货了
输出：负面"""

prompt = template.format(
    instruction="判断情感，只输出正面或负面",
    examples=examples,
    query="物流很快，包装完好"
)
print(prompt)
```

**分隔符**（delimiter）如 `###`、`---`、`输入：` 能帮助模型区分任务与样例，减少混淆。

---

## 4. 少样本提示的核心技巧

### 4.1 格式一致性
示例的输出格式必须和期望输出**完全一致**（大小写、标点、语言）。

### 4.2 标签平衡
分类任务中，正面和负面样例数量尽量均衡，否则模型会偏向多数类。

### 4.3 示例顺序有影响
把**最接近查询**的示例放在最后（靠近 Query），模型更容易模仿。

```python
# 按相似度排序示例（伪代码）
examples = sorted(examples, key=lambda e: similarity(e, query))
# 相似度低的放前面，高的放最后
```

### 4.4 Few-Shot vs 微调（Fine-Tuning）

| 维度 | Few-Shot | 微调 |
|------|----------|------|
| 成本 | 极低（改 prompt） | 高（训练 + 数据） |
| 灵活性 | 随时改 | 需重新训练 |
| 适用 | 格式控制、简单分类 | 复杂领域、大量数据 |

---

## 5. 工程实践：把 Few-Shot 封装成函数

真实项目中，示例通常从配置文件或数据库中读取，动态拼进 prompt。

```python
# 可复用的少样本分类器
import openai  # 假设已配置 API Key

def few_shot_classify(text, examples, labels=("正面", "负面")):
    # 拼接示例
    demo = "\n\n".join(
        f"输入：{x}\n输出：{y}" for x, y in examples
    )
    prompt = (
        f"判断情感，只输出{'或'.join(labels)}。\n\n"
        f"{demo}\n\n输入：{text}\n输出："
    )
    # 实际调用（此处示意）
    # resp = openai.ChatCompletion.create(...)
    # return resp.choices[0].message.content.strip()
    return prompt  # 演示用，返回 prompt

# 使用
samples = [
    ("味道很好", "正面"),
    ("上菜太慢", "负面"),
    ("服务态度差", "负面"),
]
print(few_shot_classify("环境安静，适合聊天", samples))
```

**关键结论**：Few-Shot 的工程价值在于**用最小成本控制 LLM 的输出格式和行为**，是构建 Agent（智能体）的基础技能之一。

---

## 6. 常见误区速览（详见 pitfalls）

- 示例太多 → 占满上下文（context window），反而降低效果。
- 示例格式不统一 → 模型输出混乱。
- 示例标签不平衡 → 模型偏向多数类。
- 把答案泄露到 Query 中 → 模型直接抄答案。
