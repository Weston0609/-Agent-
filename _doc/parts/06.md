# 第六章 本地化部署：从一台笔记本到私有化集群

本地部署是「数据不出门」和「成本可控」的唯一解，但也是坑最多的环节。这一章按「硬件 → 模型 → 引擎 → 部署方式 → 调优 → 排错」的顺序讲。

## 6.1 先搞清楚你要的是哪种「本地化」

很多人把四件事混为一谈，导致方案选错：

| 类型 | 含义 | 典型方案 | 成本量级 |
| --- | --- | --- | --- |
| 个人本地 | 自己电脑上跑，学习/试用 | Ollama / LM Studio | 0 元（用现有显卡） |
| 单机私有 | 一台服务器，团队内部用 | Docker + vLLM + Dify | 1～5 万元硬件 |
| 集群私有 | 多卡多机，全公司用 | K8s + vLLM 集群 + 网关 | 30 万～数百万 |
| 混合云 | 敏感数据本地，通用能力上云 | 本地小模型 + 云端大模型路由 | 弹性 |

**决策依据只有三条**：数据能不能出内网、并发多少、预算多少。这三条一定，方案就定了。

## 6.2 硬件选型：显存决定一切

### 显存需求速查表

| 模型规模 | FP16 权重 | INT8 | INT4 | 推荐显卡 | 能扛的并发（8K 上下文） |
| --- | --- | --- | --- | --- | --- |
| 1.5B～3B | 3～6 GB | 2～3 GB | 1～2 GB | RTX 3060 12G / 4060Ti 16G | 20+ |
| 7B～8B | 14～16 GB | 8 GB | 5 GB | RTX 4090 24G / A10 24G | 8～15 |
| 14B | 28 GB | 15 GB | 9 GB | A6000 48G / L40S 48G | 8～12 |
| 32B | 64 GB | 33 GB | 20 GB | 2×A6000 / A100 40G | 4～8 |
| 70B～72B | 140 GB | 72 GB | 40 GB | 4×A100 80G / 8×L40S | 4～10 |
| 671B MoE（激活 37B） | 1300 GB | 700 GB | 400 GB | 8×H200 或更多 | 视配置 |

**几个反直觉的事实**：

- **消费级显卡跑不了大模型，不是因为算力，是因为显存**。4090 算力很强，但 24 GB 显存决定了它最多舒服地跑 14B 量化版。
- **MoE 模型省算力但不省显存**。DeepSeek-V3 激活参数只有 37B，但全部权重都得加载，显存需求按 671B 算。
- **多卡不是简单相加**。2 张 24G 卡跑 32B 模型，通信开销会让吞吐远低于理论值。

### 硬件采购建议（2026 年视角）

| 预算 | 推荐配置 | 能干什么 |
| --- | --- | --- |
| 0（用现有电脑） | 有独显就行 | 7B 量化版，个人学习 |
| 1～2 万 | RTX 4090 24G 单卡工作站 | 14B 量化版，小团队内部工具 |
| 5～8 万 | 2×L40S 48G 或 4×4090 | 32B，20 人团队 |
| 20～40 万 | 4×A100 80G 或 8×L40S | 70B，百人团队 |
| 100 万+ | 8×H100/H200 集群 | 大 MoE，全公司 |

> 国产卡（昇腾 910B、海光 DCU、寒武纪）在信创项目里是刚需，但软件生态适配成本要算进去：模型转换、算子支持、推理引擎（用 LMDeploy / MindIE）都要额外验证，周期通常比 NVIDIA 方案多 2～4 周。

## 6.3 部署方式：五种，从简单到专业

### 方式一：Ollama（10 分钟上手）

```bash
# 安装后
ollama pull qwen2.5:7b
ollama run qwen2.5:7b

# 它自动在 11434 端口起 OpenAI 兼容服务
curl http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"qwen2.5:7b","messages":[{"role":"user","content":"你好"}]}'
```

**适合**：学习、Demo、个人助手、离线环境。
**不适合**：生产（默认单并发、无批处理、无监控、无鉴权）。

**必须做的加固**（如果要在内网用）：

```bash
# 1. 只监听本机，避免整个内网白嫖
OLLAMA_HOST=127.0.0.1:11434 ollama serve

# 2. 限制模型常驻内存，避免 OOM
OLLAMA_MAX_LOADED_MODELS=1
OLLAMA_NUM_PARALLEL=4

# 3. 前面挂一层 Nginx 做鉴权和限流
```

### 方式二：llama.cpp（CPU / Mac / 端侧）

```bash
# 编译（或用预编译包）
git clone https://github.com/ggerganov/llama.cpp && cd llama.cpp
cmake -B build && cmake --build build --config Release -j

# 下载 GGUF 量化模型后启动服务
./build/bin/llama-server \
  -m models/qwen2.5-7b-instruct-q4_k_m.gguf \
  --host 0.0.0.0 --port 8080 \
  -c 8192 -ngl 99 \        # -ngl 99 = 全部层放 GPU，纯 CPU 就设 0
  --parallel 4
```

**适合**：Mac（Metal 加速很好）、无 GPU 服务器、树莓派、离线设备、需要极致量化的场景。
**优点**：量化格式最丰富（Q2～Q8）、内存占用可控、跨平台。
**缺点**：并发能力弱，长上下文性能下降明显。

### 方式三：vLLM（生产首选）

```bash
# Docker 方式（推荐，避免环境地狱）
docker run --gpus all --shm-size 16g -p 8000:8000 \
  -v ~/.cache/huggingface:/root/.cache/huggingface \
  vllm/vllm-openai:latest \
  --model Qwen/Qwen2.5-14B-Instruct \
  --served-model-name qwen14b \
  --max-model-len 16384 \
  --gpu-memory-utilization 0.92 \
  --max-num-seqs 32 \
  --enable-prefix-caching \
  --api-key sk-internal-xxx
```

**关键参数详解**：

| 参数 | 作用 | 调优建议 |
| --- | --- | --- |
| `--max-model-len` | 单请求最大上下文 | 按真实需求设，别直接拉满 |
| `--gpu-memory-utilization` | 显存占用上限 | 0.85～0.92；与其他进程共卡时降到 0.6 |
| `--max-num-seqs` | 并发序列数 | 显存够就调大，延迟敏感就调小 |
| `--tensor-parallel-size` | 张量并行卡数 | 等于 GPU 数，取 2 的幂 |
| `--enable-prefix-caching` | 前缀缓存 | 系统提示长时必开 |
| `--quantization` | 量化方式 | `awq` / `gptq` / `fp8` |
| `--max-num-batched-tokens` | 单批最大 token | 影响吞吐与延迟的平衡点 |
| `--swap-space` | CPU 交换空间 | 显存紧张时调大，但会变慢 |

### 方式四：Docker Compose 全家桶（推荐给中小团队）

一个 `docker-compose.yml` 起完整栈：

```yaml
services:
  vllm:
    image: vllm/vllm-openai:latest
    runtime: nvidia
    command: >
      --model Qwen/Qwen2.5-7B-Instruct
      --served-model-name qwen7b
      --max-model-len 8192
      --gpu-memory-utilization 0.85
      --api-key sk-internal-xxx
    ports: ["8000:8000"]
    volumes: ["~/.cache/huggingface:/root/.cache/huggingface"]
    deploy:
      resources:
        reservations:
          devices: [{driver: nvidia, count: 1, capabilities: [gpu]}]
    restart: unless-stopped

  gateway:
    image: ghcr.io/berriai/litellm:main-latest
    command: ["--config", "/app/config.yaml", "--port", "4000"]
    volumes: ["./litellm.yaml:/app/config.yaml"]
    ports: ["4000:4000"]
    depends_on: [vllm]
    restart: unless-stopped

  dify-api:
    image: langgenius/dify-api:latest
    environment:
      - OPENAI_API_BASE=http://gateway:4000/v1
      - OPENAI_API_KEY=sk-gateway-master
    depends_on: [gateway]
    restart: unless-stopped

  qdrant:
    image: qdrant/qdrant:latest
    ports: ["6333:6333"]
    volumes: ["./qdrant_data:/qdrant/storage"]
    restart: unless-stopped
```

配套的 `litellm.yaml`：

```yaml
model_list:
  - model_name: qwen7b
    litellm_params:
      model: openai/qwen7b
      api_base: http://vllm:8000/v1
      api_key: sk-internal-xxx
  - model_name: deepseek
    litellm_params:
      model: deepseek/deepseek-chat
      api_key: os.environ/DEEPSEEK_API_KEY

general_settings:
  master_key: sk-gateway-master
  database_url: postgresql://user:pass@postgres:5432/litellm

litellm_settings:
  drop_params: true
  set_verbose: false
```

### 方式五：K8s 集群（大厂/私有云）

核心组件：

| 组件 | 作用 | 选型 |
| --- | --- | --- |
| GPU 调度 | 分配 GPU 资源 | NVIDIA device plugin / GPU Operator |
| 推理服务 | 跑模型 | vLLM（自建 Deployment）或 KServe |
| 自动扩缩 | 按 QPS 扩副本 | HPA + 自定义指标（队列长度） |
| 模型加载加速 | 避免每次拉权重 | 本地 NVMe 缓存 / 模型预热 |
| 网关 | 统一入口 | LiteLLM / APISIX / Higress |
| 监控 | GPU 利用率、TTFT | DCGM Exporter + Prometheus + Grafana |

**K8s 上跑推理的三个特有难点**：

1. **冷启动慢**：70B 模型加载要 5～15 分钟，HPA 扩容根本来不及。解法是**预留最小副本 + 模型预加载 + 用更快的存储**。
2. **GPU 碎片**：一张卡只能给一个 Pod 用，导致利用率低。解法是 MIG 切分（A100/H100）或时间片共享。
3. **长连接与负载均衡**：流式响应是长连接，普通轮询 LB 会导致请求堆积在某个副本。解法是**最少连接数策略 + 会话保持**。

## 6.4 模型下载与国内加速

国内直接从 HuggingFace 拉权重经常超时。三个办法：

```bash
# 1. 用镜像站
export HF_ENDPOINT=https://hf-mirror.com
huggingface-cli download Qwen/Qwen2.5-7B-Instruct --local-dir ./models/qwen7b

# 2. 用 ModelScope（阿里，国内最稳）
pip install modelscope
modelscope download --model Qwen/Qwen2.5-7B-Instruct --local_dir ./models/qwen7b

# 3. 离线拷贝：在能联网的机器下载后用 U 盘/内网传输
```

**离线部署清单**（断网环境必备）：

- 模型权重文件（含 tokenizer、config.json）
- 推理引擎镜像（`docker save` 成 tar）
- Python 依赖 wheel 包（`pip download -r requirements.txt`）
- 基础镜像（CUDA 运行时）
- 一份 `README-部署.md`，写清楚每一步命令

## 6.5 性能调优：从「能跑」到「跑得好」

### 压测方法

不要凭感觉。用工具压出真实数据：

```bash
# 用 vLLM 自带 benchmark
python benchmarks/benchmark_serving.py \
  --backend openai-chat \
  --base-url http://localhost:8000 \
  --model qwen7b \
  --dataset-name random \
  --num-prompts 200 \
  --request-rate 10 \
  --random-input-len 1024 \
  --random-output-len 256
```

输出会给你 **TTFT、TPOT、吞吐、P99 延迟**。这才是能写进方案的数。

### 调优优先级（从收益最大开始）

1. **开前缀缓存**：系统提示长 → TTFT 降 40%～70%。
2. **量化**：FP16 → AWQ INT4，显存减半，吞吐提升 1.5～2 倍，质量损失 1%～3%。
3. **调 `max-num-seqs`**：从 8 试到 128，找吞吐与延迟的拐点。
4. **限制 `max_tokens`**：输出长度是成本的最大变量。
5. **上下文裁剪**：把 32K 降到 8K，显存和延迟双降。
6. **换引擎**：vLLM → SGLang，在结构化输出密集场景能再提 20%～40%。
7. **加卡 / 换卡**：最后手段，最贵。

### 一个真实的优化案例（数字可复现）

```text
初始：Qwen2.5-14B FP16，单卡 A6000，max-model-len=32768
      TTFT 2.8s，TPOT 45ms，吞吐 380 tokens/s，并发 4 就 P99 超 20s

优化 1：max-model-len 降到 8192            → 显存释放，max-num-seqs 提到 16
优化 2：开 prefix caching                  → TTFT 降到 1.1s
优化 3：换 AWQ INT4 量化                   → 显存再省一半，max-num-seqs 提到 32
优化 4：max_tokens 上限设 1024（业务够用）  → 单请求成本降 40%

结果：TTFT 0.9s，TPOT 38ms，吞吐 1150 tokens/s，并发 20 时 P99 8s
```

**这个案例说明一件事：调优的收益主要来自「砍需求」，不是「堆硬件」。**

## 6.6 部署排错手册

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `CUDA out of memory` | 显存不够 | 降 `max-model-len` / 降 `gpu-memory-utilization` / 量化 / 加卡 |
| 启动卡在加载权重 | 磁盘慢或网络拉取 | 本地缓存权重、用 NVMe |
| 首次请求极慢 | 模型冷启动、CUDA 编译 | 预热请求、`--enforce-eager` 关掉图优化 |
| 并发一高就超时 | `max-num-seqs` 太小或显存不足 | 调参或加卡 |
| 输出乱码/重复 | 量化过度（Q2/Q3）或采样参数错 | 用 Q4 以上，检查 temperature/top_p |
| 中文答英文 | 模型本身中文弱或系统提示是英文 | 换中文模型，系统提示用中文 |
| 端口能通但返回 404 | 少了 `/v1` 前缀 | 检查 base_url |
| 容器内 GPU 不可见 | 未装 nvidia-container-toolkit | `--gpus all` + 检查 `nvidia-smi` |
| 多卡比单卡还慢 | TP 通信开销 > 收益 | 减少 TP 数，或换 NVLink 机型 |
| 长文本回答截断 | `max-model-len` 或 `max_tokens` 限制 | 调整参数，注意输入+输出总和 |

## 6.7 成本对比：自建 vs 云 API（务必自己算一遍）

```text
自建（Qwen2.5-14B，A6000 单卡）：
  硬件 4 万（折旧 3 年）      ≈ 1111 元/月
  电费 400W × 24h × 30 × 0.8  ≈ 230 元/月
  运维人力 0.2 人             ≈ 3000 元/月
  ─────────────────────────────────────
  固定成本                    ≈ 4341 元/月
  能支撑：约 20 并发，日均 5 万次短请求

云 API（同等能力，按 0.008 元/次算）：
  5 万次/日 × 30 × 0.008      ≈ 12000 元/月
```

**结论**：日均请求量超过约 1.5 万次时，自建开始划算；低于这个量，云 API 更省。但如果有**数据合规硬要求**，成本就不是第一考量了。

> 还有第三种选择：**混合**。敏感数据走本地小模型，通用问答走云 API，用网关按规则路由。这是目前企业最主流的做法。
