# 第一章 先把地基打穿：AI 应用到底在跑什么

这一章不讲任何框架的名字。先把「一个 AI 应用从你敲下回车到屏幕上出字」这条链路彻底拆开。拆开之后你会发现：后面所有框架、所有协议、所有网关，都只是这条链路上某一段的封装。看不懂框架，通常是因为没看清它包的是哪一段。

## 1.1 一句话世界观：五层积木

任何 AI 系统，无论叫 Agent、叫 RAG、叫工作流，都能拆成下面五层。记住这张图，后面每一章都是在给某一层填细节。

| 层 | 它负责什么 | 典型代表 | 你打交道的形态 |
| --- | --- | --- | --- |
| 应用层 | 业务逻辑、界面、权限、计费 | 你的产品、Dify 应用、Coze Bot | 网页 / App / 接口 |
| 编排层 | 决定「下一步调谁」、拼上下文、管循环 | LangGraph、CrewAI、Agents SDK、Dify 工作流 | 代码或可视化画布 |
| 协议层 | 让不同程序按统一格式说话 | MCP、OpenAI 兼容 API、A2A、OpenAPI | JSON / SSE 流 |
| 推理层 | 把权重跑成 token，管显存和并发 | vLLM、SGLang、Ollama、llama.cpp | HTTP 服务 |
| 模型层 | 权重本身，一个概率函数 | DeepSeek、Qwen、Llama、GPT、Claude | 文件 / 云端 API |

横向还挂三条支撑线：**数据线**（向量库、对象存储、知识库）、**治理线**（网关、密钥、限流、审计、评测）、**运维线**（容器、K8s、监控、日志）。

> 一个非常常见的误解：以为「用了某个框架就等于有了 Agent」。事实是，框架只解决编排层的代码组织问题。一个 Agent 好不好用，80% 取决于模型能力、上下文质量和工具设计，框架只占很小的权重。这也是为什么同一套 LangGraph 代码，换个模型效果天差地别。

## 1.2 模型底层：它其实只会一件事

### 从文字到数字：分词

模型不认识汉字，也不认识英文单词。第一步是把文本切成 **token**（子词单元），每个 token 映射成一个整数 ID。中文大致 1 个汉字 ≈ 1～1.5 个 token，英文约 4 个字符 ≈ 1 个 token。这个比例直接决定了你的账单——计费按 token 算，不按字数算。

分词器（tokenizer）是模型自带的，不能换。不同模型的分词表不同，所以「同一个提示词在不同模型上消耗的 token 数不一样」，这会导致成本估算出现偏差。

### 注意力：Transformer 的核心

一句话概括：**每个 token 都去问其他所有 token「你和我有多相关」，然后按相关度把信息加权汇总过来。**

```text
输入 X  ──线性变换──>  Q (查询)  K (键)  V (值)
注意力权重 = softmax( Q·Kᵀ / √d )
输出       = 注意力权重 · V
```

- **Q·Kᵀ** 算的是「相关性打分」；除以 **√d** 是防止数值过大导致 softmax 饱和（梯度消失）。
- **多头（Multi-Head）**：同时用多组 Q/K/V，让模型在同一层里并行关注「语法关系」「指代关系」「事实关联」等不同维度。
- **因果掩码（Causal Mask）**：生成式模型只允许看左边、不许看右边，保证「预测下一个词」时没有偷看答案。
- 上面这层做完，过一个**前馈网络（FFN）** 做非线性变换，再叠加**残差连接 + 归一化**，重复 N 层（7B 模型通常 32 层，70B 约 80 层）。

**位置信息**靠位置编码注入。现在主流是 **RoPE（旋转位置编码）**，它把位置信息编码成旋转角度，好处是天然支持外推，这也是「长上下文」能力的技术基础之一。

### 从向量到文字：采样

最后一层输出每个词表位置上的分数（logits），softmax 成概率，然后按策略挑一个：

| 参数 | 作用 | 实践取值 |
| --- | --- | --- |
| temperature | 温度越高越随机 | 事实类 0～0.3，创意类 0.7～1.0 |
| top_p | 只从累计概率前 p 的词里采样 | 0.9～0.95，一般不要和 temperature 同时大调 |
| top_k | 只从概率最高的 k 个词里选 | 40 左右 |
| repetition_penalty | 惩罚重复 | 1.0～1.1，太高会说话变怪 |
| max_tokens | 输出上限 | 按场景卡死，防止跑飞烧钱 |

### KV Cache：为什么长上下文这么贵

生成是逐 token 的。第 N 个 token 计算注意力时，前面所有 token 的 K 和 V 都没变，没必要重算，缓存起来即可——这就是 **KV Cache**。

它的显存占用近似为：

```text
KV 显存 ≈ 2 × 层数 × KV头数 × 头维度 × 序列长度 × 批大小 × 每元素字节数
```

以 Llama-3-8B（32 层、8 个 KV 头、头维度 128、FP16）为例，单个请求 32K 上下文：

```text
2 × 32 × 8 × 128 × 32768 × 2 字节 ≈ 4.3 GB
```

**只要一个请求就吃掉 4 GB 显存**，而这还没算模型权重（8B 的 FP16 约 16 GB）。这就是「32K 上下文很贵」的物理原因，也是 PagedAttention、GQA/MQA、KV 量化这些技术存在的理由。

### 训练与后训练：能力从哪来

| 阶段 | 做了什么 | 结果 |
| --- | --- | --- |
| 预训练 | 海量文本上做下一个词预测 | 获得语言与知识，但不会听指令 |
| SFT 监督微调 | 用「问题-标准答案」对训练 | 学会按格式回答 |
| 偏好对齐（RLHF / DPO） | 用人类偏好数据调 | 更听话、更安全、更少胡说 |
| 推理时扩展 | CoT、自一致性、多次采样投票 | 用算力换准确率 |

**关键结论：模型是无状态的。** 它不记得你上一轮说了什么，所谓「多轮对话」是每次把你的历史消息重新拼进去再发一遍。想通这一点，你就理解了：记忆系统、上下文管理、会话压缩，全部是**外部工程**，不是模型自带的魔法。

## 1.3 推理引擎底层：为什么生产环境不能只用 Ollama

模型权重是死的，要变成能扛并发的 HTTP 服务，中间需要一层推理引擎。这一层的技术含量被严重低估。

### 三个核心优化

**PagedAttention（分页注意力）**：把 KV Cache 像操作系统管理内存一样切成固定大小的块（block），按需分配、非连续存储。效果是把显存浪费从 60%～80% 降到个位数，吞吐提升 2～4 倍。这是 vLLM 的立身之本。

**连续批处理（Continuous Batching）**：传统批处理要等一个 batch 里所有请求都生成完才能接下一批；连续批处理是「谁生成完了就把它的位置让给新请求」，GPU 几乎不空转。这是吞吐翻几倍的关键。

**前缀缓存（Prefix Caching）**：系统提示词、工具定义、RAG 检索到的长文档，每次请求都一样。把这段的 KV 缓存下来复用，首字延迟能砍掉一半以上。所有主流引擎都支持，且很多厂商 API 也有「缓存命中打折」。

### 衡量指标：别只看「每秒多少字」

| 指标 | 含义 | 用户感知 |
| --- | --- | --- |
| TTFT | 首 token 延迟 | 点了之后多久开始出字 |
| TPOT / ITL | 相邻 token 间隔 | 出字是否流畅 |
| 吞吐（tokens/s） | 全系统每秒产出 | 决定成本 |
| 并发数 | 同时服务的请求数 | 决定容量 |
| Goodput | 满足 SLO 的有效吞吐 | 唯一真正该看的指标 |

一个残酷现实：**吞吐和延迟是对立的**。把 batch 开大，吞吐上去了，单请求延迟就变差。生产环境必须按 SLO 定 batch 策略，而不是追峰值吞吐。

### 引擎选型速查

| 引擎 | 定位 | 适合 | 不适合 |
| --- | --- | --- | --- |
| vLLM | 生产级通用首选 | NVIDIA GPU 集群、高并发 API | 极端低延迟、非 NVIDIA 硬件 |
| SGLang | 高吞吐 + 复杂结构化生成 | 大规模、RadixAttention 前缀复用强的场景 | 生态工具链不如 vLLM 成熟 |
| LMDeploy | 国产化 / 多硬件 | 昇腾、昆仑等国产卡，InternLM 系 | 社区规模较小 |
| TensorRT-LLM | 极致性能 | 愿意做编译优化、固定模型 | 迭代快、模型常换的团队 |
| llama.cpp | CPU / 端侧 / 量化 | 笔记本、Mac、树莓派、边缘设备 | 高并发服务 |
| Ollama | 一键跑模型 | 个人试用、本地开发、Demo | 生产并发（默认单并发、调度弱） |
| TGI | HuggingFace 官方 | HF 生态用户 | 更新节奏放缓，新模型适配慢 |

> 经验法则：**学习和验证用 Ollama，上线用 vLLM，国产卡用 LMDeploy，端侧用 llama.cpp。** 不要用 Ollama 承载生产流量，它的默认配置是给「一个人用」设计的。

## 1.4 Agent 底层：剥掉包装就是一个 while 循环

所有 Agent 框架，剥到最里层都是这段伪代码：

```python
messages = [system_prompt, user_question]
while True:
    resp = llm.chat(messages, tools=tool_schemas)      # 1. 调模型
    if resp.tool_calls:                                 # 2. 要调工具？
        for call in resp.tool_calls:
            result = execute(call)                      # 3. 执行
            messages.append(tool_result(call, result))  # 4. 结果塞回上下文
        continue                                        # 5. 再问一次
    return resp.content                                 # 6. 不调工具就结束
```

三个本质：

1. **上下文构造**：每一轮发给模型的东西，都是「系统提示 + 历史 + 工具结果」重新拼出来的。拼什么、拼多少、怎么压缩，决定成败。
2. **工具调用**：模型并不真的执行代码，它只输出一段 JSON 说「我想调 weather(city=北京)」，真正执行的是你的程序。
3. **循环终止**：靠模型自己判断「不需要工具了」，或者靠你设的最大轮数、超时、预算兜底。

### 三种主流范式

| 范式 | 机制 | 优点 | 缺点 |
| --- | --- | --- | --- |
| ReAct | 思考→行动→观察，循环 | 简单、可解释、通用 | 步数多、token 贵、容易绕圈 |
| Plan-and-Execute | 先出完整计划再逐步执行 | 全局性强、可控 | 计划错了全错，重规划成本高 |
| Reflexion / 自反思 | 执行后自评，失败则修正重试 | 质量上限高 | 延迟翻倍，可能陷入自我否定 |

### 为什么 Agent 不稳定——四个真实原因

- **误差累积**：每步 95% 正确率，10 步之后只剩 60%。链越长越不可靠，所以生产 Agent 的步数通常限制在 3～8 步。
- **上下文污染**：一次错误的工具结果进了上下文，后面每一步都在错误前提上推理。解法是结构化结果 + 显式纠错。
- **工具描述质量**：模型只能靠工具名和描述决定用哪个。描述含糊 = 选错工具。工具描述是 Prompt，不是注释。
- **模型能力天花板**：小模型做不了复杂多步规划。7B 模型做单步工具调用可以，做 20 步业务流程基本必崩。

## 1.5 上下文工程：2026 年最值钱的技能

Prompt Engineering 是「怎么把一句话说好」，Context Engineering 是「怎么把一整个上下文窗口安排好」。后者才是工程。

### 上下文窗口里该放什么

```text
┌─────────────────────────────────┐
│ 系统提示（角色/规则/输出格式）      │  ← 稳定，可缓存
│ 工具定义（名称/描述/参数 schema）   │  ← 稳定，可缓存
│ 长期记忆（用户画像/历史偏好）       │  ← 半稳定
│ 检索内容（RAG 片段，带引用编号）    │  ← 每轮变化
│ 会话历史（近期对话，旧的压缩）      │  ← 滚动
│ 当前用户输入                       │  ← 最新
│ 输出预算（预留空间）               │  ← 别忘了留
└─────────────────────────────────┘
```

### 四条硬规则

1. **中间会丢**：模型对上下文开头和结尾最敏感，中间部分容易被忽略（Lost in the Middle）。重要信息放头尾。
2. **长 ≠ 好**：上下文塞满会显著降低准确率（Context Rot）。宁可检索 3 条精准的，不要塞 30 条含糊的。
3. **压缩要有损控制**：历史超过阈值就摘要，但摘要必须保留「已确认的事实、已做的决定、待办事项」三类，否则 Agent 会反复问同样的问题。
4. **结构化优于散文**：给模型 JSON / 表格 / 明确分隔符，比给一大段自然语言稳定得多。

## 1.6 RAG 底层：检索增强生成到底在补什么

模型的三个硬伤：知识有截止日期、不知道你的私有数据、会一本正经胡说。RAG 就是「开卷考试」——先去你的资料里查，把查到的内容塞进上下文，再让模型基于材料回答。

### 完整链路

```text
离线：文档 → 解析(OCR/表格) → 清洗 → 切分(chunk) → 向量化(embedding) → 入库
在线：问题 → (查询改写) → 向量化 → 混合检索(向量+关键词) → 重排(rerank)
      → 取 Top-N → 拼 Prompt(带编号) → 生成(要求引用) → 返回 + 溯源
```

### 每个环节的坑

| 环节 | 常见错误 | 正确做法 |
| --- | --- | --- |
| 解析 | PDF 直接文本抽取，表格全乱 | 用版面分析工具；表格单独结构化 |
| 切分 | 固定 512 字符硬切，句子被切断 | 按语义/标题层级切，带 10%～20% 重叠 |
| 向量化 | 中文用英文模型 | 选多语言/中文优化模型，维度与库对齐 |
| 检索 | 只做向量检索 | 向量 + BM25 混合，专有名词才查得准 |
| 重排 | 不做 rerank | 召回 50 条，rerank 后取 5 条，效果提升最明显 |
| 生成 | 不要求引用 | 强制输出 `[1][2]` 编号，无依据就说「资料中没有」 |
| 评测 | 凭感觉 | 建 50～100 条问答对，算召回率与答案准确率 |

### RAG 的三个进阶形态

- **GraphRAG**：把文档抽成实体关系图，适合「跨多篇文档做关联推理」的问题，代价是构建成本高。
- **Agentic RAG**：让 Agent 自己决定查什么、查几次、要不要换关键词，适合复杂多跳问题，代价是延迟和成本。
- **多模态 RAG**：图文混排文档，先做版面理解再检索，适合手册、财报、图纸。

## 1.7 一次完整调用的时序：钱花在哪，故障出在哪

```text
用户提问
   │
   ├─> [1] 应用层：鉴权、拼会话、取用户配置
   │
   ├─> [2] 网关层：校验 key、限流、选模型、记日志  ← 计费起点
   │
   ├─> [3] 编排层：检索知识库 / 组装系统提示 / 挂载工具
   │        │
   │        └─> [4] 推理层：prefill(吃输入) + decode(吐输出)
   │                  ↑ TTFT 主要花在这
   │
   ├─> [5] 模型返回 tool_call
   │        │
   │        └─> [6] MCP / 工具服务：查数据库、调 API、读文件
   │
   ├─> [7] 结果回填上下文，再走一次 [4]  ← 第二轮计费
   │
   └─> [8] 流式返回给用户，落日志、算成本、写评测样本
```

记住这个时序，第五章的「故障分层定位表」就是按它逐段排查的。**90% 的线上问题都能通过「卡在哪一段」快速缩小范围**：首字慢是推理层或网关层；出字卡顿是推理层 batch 太大；答案错是编排层或数据层；工具报错是工具层。
