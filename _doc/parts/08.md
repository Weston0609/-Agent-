# 第八章 不会写代码，如何用 AI 产出高质量的东西

这一章是全书最"反直觉"的一章，因为我要先讲一个坏消息，再讲好消息。

**坏消息**：AI 不会让你从「不会」变成「会」。它只会把你「模糊的想法」放大成「模糊的产品」，或者把你「清晰的想法」放大成「清晰的产品」。**输入的质量决定输出的质量，这个规律没有被 AI 打破，反而被放大了。**

**好消息**：让想法变清晰，本身不需要会写代码。它需要的是**结构化思维**。而结构化思维是可以练的，且比学编程快得多。

## 8.1 先认清 AI 的能力边界

### AI 擅长什么（可以放心外包）

| 能力 | 说明 | 典型任务 |
| --- | --- | --- |
| 模式识别与转换 | 把一种形式转成另一种 | 需求文档 → 代码、代码 → 文档、SQL → 自然语言 |
| 广度覆盖 | 见过的东西多 | 生成 20 个方案让我挑、列出 50 个边界情况 |
| 语言润色 | 表达优化 | 改写成正式文档、翻译、调整语气 |
| 样板生成 | 重复性结构 | CRUD 接口、配置文件、测试脚手架 |
| 解释与教学 | 把不懂的讲明白 | 解释报错、解释这段代码在干什么 |
| 一致性检查 | 找矛盾 | 代码与文档不一致、命名不统一 |

### AI 不擅长什么（别外包）

| 能力 | 为什么不行 | 后果 |
| --- | --- | --- |
| 判断「该不该做」 | 它不知道你的业务约束、政治环境、真实优先级 | 做出一个没人要的东西 |
| 承担后果 | 它不会因为线上事故被开除 | 决策责任必须你自己扛 |
| 知道你的隐含上下文 | 你没说的它不知道，你说了错的它就信 | 基于错误前提给出完美推理 |
| 长期一致性 | 每次对话都是新开始（除非你给它记忆） | 今天这样、明天那样 |
| 判断「对不对」 | 它会自信地说错话 | 你信了，就完了 |
| 品味与取舍 | 它给平均值，不给最优解 | 产品平庸 |

**一句话总结**：**AI 是极强的执行者，极差的决策者。** 你要做的是把所有决策权留在自己手里，把执行外包出去。

## 8.2 高质量输出的四要素（缺一不可）

我把它总结成 **CRAFT** 模型：

| 要素 | 含义 | 缺失后果 |
| --- | --- | --- |
| **C**ontext 上下文 | 背景、约束、已有条件 | 答非所问，泛泛而谈 |
| **R**ole 角色 | 让它以什么身份思考 | 视角错位，深度不够 |
| **A**sk 任务 | 具体要什么，输出什么格式 | 输出不可用，要反复改 |
| **F**ormat 格式 | 结构化要求 | 无法直接使用，要人工整理 |
| **T**est 验证 | 怎么判断它做对了 | 你不知道它错没错 |

### 反例 vs 正例

**反例**（90% 的人这样问）：

> 帮我写一个客服系统。

结果：给你一个玩具级 demo，字段名全是 `foo`、`bar`，没有异常处理，跑不起来。

**正例**：

```text
【背景】我们是做跨境电商的，日均咨询 3000 条，客服 8 人。
现在的问题：60% 的咨询是重复问题（物流、退换货政策），人工回复慢，客户满意度低。
已有资源：一套产品文档（PDF 约 200 页）、一个订单查询 REST API（GET /orders/{id}）。
约束：数据不能出境，必须私有化部署；预算每月 3000 元以内；2 周内出可用版本。

【角色】你是一个有 10 年经验的 AI 应用架构师，擅长在资源受限下做取舍。

【任务】给出一个客服助手的落地方案，要求：
1. 技术选型（含为什么选它、为什么不选另外两个）
2. 数据流图（文字描述即可，从用户提问到返回答案的每一步）
3. 关键风险与应对（至少 5 条）
4. 2 周排期（按天，标注依赖）
5. 上线后的验收指标

【格式】用 Markdown，每个部分不超过 300 字，能用表格就用表格。
【不要】不要给我代码，不要推荐需要 GPU 集群的方案。
```

差别在哪？**正例把「决策所需的信息」全给了，把「输出格式」定死了，把「不要什么」也说清楚了。**

### 提问的五个层次（自检用）

| 层次 | 提问方式 | 输出质量 |
| --- | --- | --- |
| L1 许愿 | 「帮我做个 X」 | 玩具 |
| L2 加背景 | 「我在做 Y，帮我做 X」 | 及格 |
| L3 加约束 | 「…约束是 A/B/C，不要 D」 | 良好 |
| L4 加格式 | 「…按这个结构输出」 | 可直接用 |
| L5 加验证 | 「…并给出你怎么自检、哪里可能错」 | 可交付 |

**大多数人停在 L2，然后抱怨 AI 不好用。** 你在 L4/L5，就已经超过 90% 的人了。

## 8.3 六个可复用的提示词模板

### 模板 1：需求澄清（在动手前用）

```text
我要做的是：<一句话描述>
我掌握的信息：<已知条件>
我不确定的：<列出 3~5 个你不确定的点>

请你：
1. 先不要给方案。列出为了做出正确方案，你还需要我回答的 10 个问题，按重要性排序。
2. 对每个问题，给出「如果选 A 会怎样、选 B 会怎样」的简短说明。
3. 最后指出：我上面的描述里，哪一句最可能是错的或者有歧义的。
```

**这个模板的价值**：它逼 AI 暴露「它不知道什么」，而不是直接编一个方案。你会发现自己的需求有多模糊。

### 模板 2：方案对比（做技术选型用）

```text
场景：<背景 + 约束>
候选方案：A / B / C（如果不确定，让我先列）

请用表格对比，维度必须包含：
- 上手成本（人日）
- 运行成本（月）
- 扩展性上限
- 出问题时的排查难度
- 团队需要什么技能
- 什么情况下它会成为错误选择

最后给出：在你的判断里选哪个，以及「如果我错了，最可能错在哪」。
```

**注意最后那句**——逼它说出自己的不确定性，这是判断它靠不靠谱的最好方式。

### 模板 3：代码生成（必须带验收标准）

```text
【环境】Python 3.11，只用标准库 + requests，不要引入新依赖。
【任务】实现一个函数 `fetch_orders(ids: list[str]) -> dict[str, dict]`：
- 调 GET https://api.example.com/orders/{id}
- 超时 10s，失败重试 2 次（指数退避 1s/2s）
- 单个失败不影响其他，失败的 id 在返回值里标记 error
- 返回结构：{"SO001": {"status": "ok", "data": {...}}, "SO002": {"status": "error", "msg": "timeout"}}

【要求】
1. 先写出函数签名和 docstring，等我确认再写实现。
2. 实现后，给出 5 个必须通过的测试用例（含边界：空列表、全部失败、部分失败）。
3. 指出这段代码在什么情况下会出问题。

【不要】不要用 asyncio，不要写类，不要加日志框架。
```

**「先确认签名再写实现」这一步极其重要**——它把「返工」的成本从「重写 200 行」降到「改一行」。

### 模板 4：代码审查（第八章第 5 节详述）

```text
请审查以下代码，分四类问题输出，每条必须给出「文件:行号 + 问题 + 修复建议」：
1. 正确性（会导致错误结果或崩溃的）
2. 安全（注入、越权、密钥泄露、资源耗尽）
3. 健壮性（异常未处理、边界未覆盖、并发问题）
4. 可维护性（命名、重复、过长函数、隐藏耦合）

【要求】
- 按严重程度排序，最严重的在前
- 对每条给出「不修的后果」一句话
- 最后给一个总体判断：能上线 / 修完能上线 / 重写
- 不要夸我，不要总结我写得多好
```

### 模板 5：报错排查

```text
【环境】<OS / Python 版本 / 依赖版本>
【操作】我执行了：<命令或代码>
【完整报错】
<粘贴完整 traceback，不要截断>
【我已经试过】<列出你试过的，避免它重复建议>
【我的猜测】<你的怀疑，可以错>

请：
1. 用一句话说出这个错误的根本原因（不要解释现象，说原因）。
2. 给出 3 个最可能的成因，按概率排序，每个附一个验证方法（具体命令或代码）。
3. 给出修复方案，并说明这个修复会不会引入新问题。
```

**关键**：贴完整 traceback。截断的报错等于让医生只看半张片子。

### 模板 6：把模糊需求变成可执行任务

```text
我有一个模糊的想法：<描述>
我的目标是：<业务目标>

请你：
1. 把这个想法拆成「必须做 / 应该做 / 可以做 / 不做」四档（MoSCoW）。
2. 对「必须做」的每一项，写成「作为一个<角色>，我要<功能>，以便<价值>」的格式。
3. 指出这里面哪一项是「看起来必须、其实可以砍」的。
4. 给出一个「两周能验证想法是否成立」的最小版本。
```

## 8.4 迭代：一次问对是神话，五轮收敛是常态

没有人一次就能问出完美提示词。真实的流程是这样的：

```text
第 1 轮：给背景 + 任务 → 拿到一个大概方向
第 2 轮：「第 3 点不对，因为 <原因>。请只重写第 3 点，其他不动。」
第 3 轮：「你漏了 <某个约束>，重新检查整个方案是否还成立。」
第 4 轮：「把方案压缩到 1 页，只留决策和执行步骤。」
第 5 轮：「现在扮演挑刺的人，找出这个方案最可能失败的三个地方。」
```

**三条迭代纪律**：

1. **一次只改一个维度**。不要「顺便把格式也改了、把语气也改了」，否则你不知道哪个改动起了作用。
2. **明确说「其他不动」**。否则它会顺手把你满意的部分也重写一遍。
3. **每轮结束做个决定**。是接受、是修改、还是推翻。不要让它一直生成，你一直看，最后什么也没定。

## 8.5 用 AI 写代码：能到什么程度，怎么用才不翻车

### 先说结论

| 场景 | AI 能做的比例 | 你要做的 |
| --- | --- | --- |
| 从零写一个 CRUD 服务 | 85% | 定数据模型、定接口、审查 |
| 给现有代码加功能 | 70% | 说清现有结构、指出改动点、验证 |
| 修一个明确的 bug | 80% | 提供复现步骤、验证修复 |
| 重构（有测试保护） | 75% | 确保测试覆盖、逐步验证 |
| 设计架构 | 40% | 你定，它提供选项 |
| 性能优化 | 50% | 你定位瓶颈，它给方案 |
| 处理遗留屎山 | 30% | 你拆解，它局部改 |
| 安全关键代码 | 30% | 必须人审，AI 只做初稿 |

**核心认知：AI 写代码的瓶颈不在「写」，在「验证」。** 你能多快验证，就能多快用它。

### 正确的工作流（五步）

**第 1 步：先让它读，不要让它写**

```text
这是项目结构：<tree 输出>
这是核心文件：<粘贴 2~3 个关键文件>
这是我要加的功能：<描述>

请先告诉我：
1. 这个功能应该改哪几个文件，为什么
2. 每个文件改什么，改动会不会影响其他地方
3. 有没有更简单的做法（比如已有函数可以复用）

先不要写代码。
```

**为什么这步最重要**：AI 最常见的失败不是「写错代码」，是「在错误的地方写代码」——重复造轮子、改错文件、破坏既有约定。先让它读，能挡掉 60% 的返工。

**第 2 步：小步生成，每步可验证**

不要一次让它写 500 行。按「一个函数 / 一个接口 / 一个测试」的粒度来。每步完成后：

```bash
# 每步都跑
python -m pytest tests/test_xxx.py -v
# 或至少
python -c "import your_module"
```

**第 3 步：让它自己写测试**

```text
请为刚才写的 fetch_orders 写测试，要求：
- 用 unittest，不引入 pytest 之外的依赖
- 必须覆盖：正常、空输入、全部失败、部分失败、超时、重试成功
- 用 unittest.mock 模拟 HTTP，不要真的发请求
- 每个测试的 docstring 写清「这个测试在防什么」
```

**第 4 步：让它自查**

```text
现在请审查你自己刚写的代码，站在「线上出事故」的角度：
1. 最可能出问题的三个地方
2. 有没有没处理的异常
3. 有没有资源泄漏（连接、文件、内存）
4. 有没有并发问题
5. 如果输入是恶意构造的，会怎样
```

**第 5 步：你来做最终判断**

跑一遍、看一眼、想一下「如果这个错了，最坏会怎样」。这一步不能省。

### 六个必须知道的坑

| 坑 | 表现 | 防法 |
| --- | --- | --- |
| **幻觉 API** | 调用不存在的方法/参数 | 让它标注「这个 API 出自哪个版本」，你去文档核对 |
| **过时写法** | 用已废弃的语法/库 | 明确说版本号；让它用最新稳定版 |
| **过度设计** | 一个函数拆成 5 个类 | 明确说「不要抽象，不要设计模式，能跑就行」 |
| **忽略边界** | 空值、超长、并发全不管 | 强制要求写测试，且必须含边界用例 |
| **悄悄改别处** | 修 A 的时候顺手改了 B | 要求「只改我指定的文件，其他一律不动」 |
| **自信的错误** | 说「这样肯定没问题」 | 追问「什么情况下这会失败」 |

### 一个真实的效率对比

```text
任务：给现有 FastAPI 服务加一个「按标签筛选 + 分页」的查询接口

传统方式：
  读代码 30min + 设计 15min + 写 40min + 测试 30min + 调试 20min ≈ 2.2 小时

AI 辅助（正确用法）：
  第 1 步 让它读代码、给改动方案        10min（人工判断 5min）
  第 2 步 生成接口 + schema             8min
  第 3 步 生成测试                      6min
  第 4 步 跑测试、修 2 个失败           15min
  第 5 步 人工审查 + 微调               12min
  ≈ 51 分钟，提速约 2.5 倍

AI 辅助（错误用法）：
  一次让它写全部 → 生成 400 行 → 跑不起来
  → 反复贴报错 → 它越改越乱 → 推倒重来
  ≈ 3 小时，还引入了隐藏 bug
```

**差距不在 AI，在方法。**

## 8.6 用 AI 审查代码：把「自查」变成「他查」

### 为什么必须让 AI 审

人审自己的代码有天然盲区：你写的逻辑在你脑子里是通的，你会自动跳过「你以为对」的地方。AI 没有这个包袱——它不知道你想干什么，所以它会真的逐行看。

### 审查的正确姿势

**不要**：把整个项目丢给它说「帮我看看有没有问题」。它会给一堆泛泛而谈的建议。

**要**：分层、分重点、给上下文。

#### 第一层：安全审查（最高优先级）

```text
请只做安全审查，不要评价代码风格。

代码：<粘贴>
上下文：这是一个内部 API，接收用户上传的 CSV 并解析入库。

请检查：
1. SQL 注入（有没有拼接 SQL）
2. 路径穿越（文件路径有没有用用户输入）
3. 命令注入（有没有 shell 调用）
4. 反序列化风险（pickle / yaml.load / eval）
5. 密钥硬编码
6. 资源耗尽（超大文件、超长字符串、无限循环）
7. 权限校验缺失（有没有验证调用者身份）

对每个发现的问题：给出「攻击者会怎么利用」的具体例子。
没问题也要说「检查过了，没发现」，不要为了凑数编问题。
```

#### 第二层：正确性审查

```text
请检查这段代码的逻辑正确性：
1. 边界条件（空、单元素、极大值、负数、None）
2. 异常路径（异常后状态是否一致、资源是否释放）
3. 并发（共享状态、竞态、死锁）
4. 幂等性（重复调用会不会出问题）
5. 数据类型（隐式转换、精度丢失、时区）

对每个问题给出一个能复现它的具体输入。
```

#### 第三层：可维护性审查

```text
请指出这段代码未来维护时的三个最大障碍：
1. 哪部分最难懂，为什么
2. 哪部分改动风险最高（改一处影响多处）
3. 哪个命名/结构会让新人误解

只给三个，按严重程度排序，不要列清单。
```

### 让 AI 审查更有效的四个技巧

**技巧 1：给它「审查清单」而不是「随便看看」**

```text
按这个清单逐项检查，每项给「通过/不通过/不适用」：
□ 所有外部输入都做了校验
□ 所有 IO 都有超时
□ 所有异常都被处理或明确向上抛
□ 没有裸 except
□ 没有硬编码的密钥/地址
□ 日志里没有敏感信息
□ 关键路径有测试覆盖
```

**技巧 2：让它扮演「攻击者」**

```text
现在你是一个想搞垮这个系统的攻击者。
你有合法账号，能调用这个 API。
请列出 10 种你能想到的攻击方式，按成功率排序。
```

这个视角比「帮我找 bug」有效得多，因为它在主动构造而非被动扫描。

**技巧 3：让它对比两个版本**

```text
版本 A（改动前）和版本 B（改动后）。
请只回答一个问题：B 相比 A，有没有引入新的风险？
逐条列出「A 里安全、B 里不安全」的地方。
```

这比审查全量代码精准得多，是 code review 的正确用法。

**技巧 4：要求它给「置信度」**

```text
对每个发现，标注你的置信度（高/中/低）。
低置信度的，说明你为什么不确定。
```

AI 经常「为了显得有用」而编造问题。要求标注置信度能过滤掉大部分噪音。

### AI 审查的三个局限（必须知道）

1. **它看不到运行时**。它不知道你的数据库里有什么脏数据，不知道线上并发是多少。所以它找不出「数据依赖」类 bug。
2. **它倾向于附和**。你问「这段代码有问题吗」，它常常说「有一点小问题」然后编一个。你问「这段代码对吗」，它常说是对的。**要用中性问法**：「请列出这段代码所有可能失败的方式」。
3. **它不懂你的业务规则**。「退款必须 7 天内」这种规则它不知道，除非你告诉它。

**所以：AI 审查是「第一道筛子」，不是「最后一道关」。** 关键系统必须有人审 + 测试 + 灰度。

## 8.7 不会写代码，能不能让 AI 替你做 Agent 开发？

这是最尖锐的问题，我给你一个不含糊的答案。

### 分三档看

| 档次 | 能做到吗 | 条件 | 现实结果 |
| --- | --- | --- | --- |
| **做 Demo / 内部工具** | ✅ 完全可以 | 会描述需求、会跑命令、会看报错 | 1～2 周能做出能用的东西 |
| **做小规模生产系统** | ⚠️ 勉强可以 | 加上会部署、会看日志、会做基础测试 | 3～6 个月能上线，但会踩很多坑 |
| **做核心业务系统** | ❌ 不行 | 需要能判断「哪里会炸」 | 出事故时你救不回来 |

### 为什么「Demo 可以、生产不行」

**Demo 的容错率是 100%**。跑不通就重来，没人受影响。
**生产的容错率是 0**。数据丢了、钱算错了、用户信息泄露了，你要负责。

而「判断哪里会炸」这件事，**恰恰是最需要经验的部分，也是最难被 AI 替代的部分**。AI 能告诉你「这段代码在做什么」，但它不能替你判断「这个设计在你们公司的业务量下会不会崩」。

### 那「不会代码」的人该怎么做 Agent 开发？

**路线 A：低代码平台（最快见效）**

用 Dify / Coze / FastGPT / n8n，可视化拖拽。你能做出：
- 客服机器人
- 文档问答
- 内容生成流水线
- 数据采集 + 分析 + 报告

**这些足够覆盖 80% 的企业内部需求**。而且不需要写代码。

代价：复杂逻辑受限，深度定制要写代码，性能受平台限制。

**路线 B：AI 生成 + 严格验证（能力上限更高）**

你负责：
1. 把需求拆到「一个函数能解决」的粒度
2. 让 AI 生成
3. **跑起来验证**
4. 出问题时能描述清楚现象

你必须会：跑命令、看报错、读日志、用 git。

**这条路的关键不是「会写」，是「会验证」。** 而验证能力是可以速成的——比学编程快得多。

**路线 C：找人合作（最现实）**

你负责产品、需求、验收；找一个会写代码的人（或外包）负责实现。
**这是绝大多数非技术背景创业者的真实路径**，不丢人，且成功率高。

### 一条诚实的建议

```text
如果你完全不会代码，且不打算学：
  → 走路线 A（低代码），把 AI 用在「业务价值」上，不要碰底层

如果你愿意花 3 个月学基础：
  → 学 Python 基础 + 会用 git + 会看日志 + 会写测试
  → 然后走路线 B，能力上限会高很多

如果你想做的是核心业务：
  → 必须有人懂代码。可以是合伙人、可以是员工，但不能没有
```

**「AI 能替你写代码」是真的；「AI 能替你承担代码的后果」是假的。** 想清楚这一点，你就知道该怎么定位自己了。

## 8.8 如何用 AI 为自己获利：五条真实路径

这一节只讲能落地的，不讲「AI 改变世界」这种话。

### 路径 1：把重复劳动自动化（最快回本）

**逻辑**：你的时间有价格。任何每天重复 30 分钟以上的事，都值得花 2 天做成自动化。

| 场景 | 做法 | 省下的时间 |
| --- | --- | --- |
| 周报/日报 | 固定模板 + 数据源 + AI 生成 | 每周 2 小时 |
| 会议纪要 | 录音转文字 + AI 摘要 + 待办提取 | 每次 40 分钟 |
| 邮件/消息回复 | 分类 + 模板 + AI 润色 | 每天 1 小时 |
| 数据整理 | 自然语言 → pandas 代码 | 每次 1 小时 |
| 竞品/行业调研 | 批量抓取 + AI 摘要 + 结构化 | 每次 1 天 |

**回本周期**：通常 1～2 周。这是投入产出比最高的用法，没有之一。

### 路径 2：做「AI + 你的专业」的垂直工具

**逻辑**：通用 AI 谁都能用，不值钱。**AI + 你独有的领域知识** 才值钱。

举例：
- 你懂法律 → 合同风险审查助手
- 你懂装修 → 报价单自动核对
- 你懂招聘 → 简历初筛 + 面试问题生成
- 你懂财务 → 发票分类 + 报表异常检测
- 你懂教育 → 个性化出题 + 学情分析

**关键**：领域知识是壁垒，AI 只是放大器。别人抄不走你的知识，只能抄走工具。

**变现方式**：内部提效（升职加薪）、对外 SaaS（订阅）、项目定制（一次性收费）。

### 路径 3：内容生产（门槛最低，竞争最激烈）

用 AI 做内容不是「让 AI 写」，是「用 AI 放大你的判断」。

```text
低价值做法：让 AI 写 100 篇文章 → 全是废话，没人看
高价值做法：
  你定选题（你的判断）
  → AI 做资料搜集和初稿（省 70% 时间）
  → 你加入独有观点和案例（你的价值）
  → AI 做多平台改写（一稿多发）
  → 你审核定稿
```

**收益模式**：广告、知识付费、引流到咨询/课程、社群。

**现实提醒**：纯 AI 生成的内容正在快速贬值。**有独家信息、独家经验、独家观点的内容才有价值。**

### 路径 4：承接「AI 落地」项目（To B）

大量中小企业知道要用 AI，但不知道怎么用。这是真实的需求缺口。

你能提供的：
- AI 应用咨询（诊断哪些环节能用 AI）
- 落地实施（搭 RAG、搭客服、搭工作流）
- 培训（教员工用 AI）

**报价参考**（国内市场，仅供估算）：
- 诊断咨询：5000～30000 元/次
- 小型落地项目：3～15 万元
- 企业内训：8000～30000 元/天

**前提**：你得真能交付。这一行口碑传播极快，做砸一个项目，区域内就传开了。

### 路径 5：做产品（最难，上限最高）

把 AI 能力封装成产品卖给很多人。难点不在技术，在**找到愿意付钱的人**。

**判断一个想法值不值得做，问三个问题**：
1. 谁痛？（具体到人群，不是「所有人」）
2. 现在他们怎么解决的？（如果答案是「忍着」，那可能不够痛）
3. 他们愿意付多少钱？（如果答案是「免费还行」，那就不成立）

### 一条反常识的建议

**不要一上来就想「用 AI 赚钱」。先想「用 AI 省时间」，省下来的时间去赚钱。**

前者需要找到市场，后者只需要找到自己的痛点。后者确定性高得多。
