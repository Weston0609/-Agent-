# 第三章 Agent 框架全景：逐个拆开看

这一章是全书最长的部分，因为它是你真正要「选」的东西。每个框架都按同一个模板讲：**它解决什么问题 → 怎么调（代码）→ 底层逻辑 → 优点 → 缺点 → 什么时候用**。

## 3.1 先把框架分成四类，你就不会迷路

市面上的「AI 框架」有上百个，但按定位只有四类，选错类别比选错框架更致命：

| 类别 | 本质 | 代表 | 谁该用 |
| --- | --- | --- | --- |
| 代码编排框架 | 给你一套 Python/TS 库，写代码组织 Agent | LangGraph、CrewAI、Agents SDK、Pydantic AI | 工程师、要深度定制 |
| 低代码平台 | 拖拽画布 + 内置模型/知识库/发布 | Dify、n8n、Coze、FastGPT、RAGFlow | 业务人员、快速验证 |
| 通用开发套件 | 大而全的「全家桶」 | LangChain、LlamaIndex、Haystack、Semantic Kernel | 需要大量现成集成 |
| 垂直工具 | 只做一件事，但做得深 | OpenHands（编码）、Aider（改代码）、Browser Use（浏览器） | 特定任务 |

**关键认知：框架不产生能力，只组织能力。** 一个 Agent 的上限由模型和工具决定，框架只影响你的开发效率和可维护性。所以选框架的第一原则是：**能用简单的不选复杂的，能用标准库的不引框架**。

## 3.2 LangChain：最早的「全家桶」，也是最大的争议点

### 它解决什么问题

2022 年时，调不同模型、接不同向量库、解析不同文档，每样都要自己写适配。LangChain 提供了统一的抽象层（`ChatModel`、`Embeddings`、`VectorStore`、`Retriever`、`Tool`），让你换后端不改代码。

### 怎么调

```python
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一个严谨的技术顾问，回答必须给出依据。"),
    ("human", "{question}"),
])

# LCEL：用管道符把组件串成链
chain = prompt | llm | StrOutputParser()
print(chain.invoke({"question": "什么是 KV Cache？"}))
```

带工具的 Agent（老式写法，现在不推荐）：

```python
from langchain.agents import create_tool_calling_agent, AgentExecutor
from langchain_core.tools import tool

@tool
def get_weather(city: str) -> str:
    """查询指定城市的实时天气。city 用中文城市名，如「北京」。"""
    return f"{city}：晴，18℃，西北风 3 级"

agent = create_tool_calling_agent(llm, [get_weather], prompt)
executor = AgentExecutor(agent=agent, tools=[get_weather], max_iterations=5)
print(executor.invoke({"question": "北京天气怎么样？"})["output"])
```

### 底层逻辑

LangChain 的核心是 **Runnable 协议**：所有组件都实现 `invoke / batch / stream / ainvoke` 四个方法，所以能用 `|` 组合成 DAG。`AgentExecutor` 内部就是一个 while 循环：调模型 → 有 tool_calls 就执行 → 结果塞回 → 再调，直到无 tool_calls 或达到 `max_iterations`。

### 优点

- 集成生态最广：几百个 loader、vector store、tool 开箱即用。
- 文档和教程最多，遇到问题搜得到答案。
- LCEL 表达力强，简单的链写起来很短。

### 缺点（必须知道）

- **抽象层太厚**：出问题时栈很深，日志难读，调试痛苦。
- **版本迭代破坏性大**：0.1 → 0.2 → 0.3 多次大改，网上大量教程已失效。
- **Agent 部分已被官方判为不推荐**：LangChain 官方明确建议复杂 Agent 用 LangGraph，`AgentExecutor` 属于遗留组件。
- **依赖重**：装一个 langchain 会拖进几十个包，启动慢。

### 什么时候用

**用**：需要快速接一堆现成集成（比如 20 种文档格式解析 + 5 种向量库对比），或者做原型验证。

**不用**：生产级复杂 Agent（用 LangGraph）、追求轻量的服务（直接调 SDK）。

## 3.3 LangGraph：当前生产级 Agent 的事实标准

### 它解决什么问题

LangChain 的链是线性的，而真实业务是**有环的**：要重试、要人工审批、要条件分支、要中断恢复。LangGraph 把 Agent 建模成**状态机 / 图**，节点是函数，边是流转条件。

### 怎么调（最小可运行示例）

```python
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import MemorySaver
from langchain_openai import ChatOpenAI

class State(TypedDict):
    messages: Annotated[list, add_messages]   # add_messages 是 reducer：追加而非覆盖

llm = ChatOpenAI(model="gpt-4o-mini")

def call_model(state: State):
    return {"messages": [llm.invoke(state["messages"])]}

def should_continue(state: State) -> str:
    last = state["messages"][-1]
    return "tools" if getattr(last, "tool_calls", None) else END

builder = StateGraph(State)
builder.add_node("agent", call_model)
builder.add_node("tools", tool_node)          # 执行工具
builder.add_edge(START, "agent")
builder.add_conditional_edges("agent", should_continue, {"tools": "tools", END: END})
builder.add_edge("tools", "agent")            # 工具执行完回到 agent —— 这就是「环」

graph = builder.compile(checkpointer=MemorySaver())
config = {"configurable": {"thread_id": "user-123"}}   # 会话隔离靠 thread_id

for chunk in graph.stream({"messages": [("user", "北京天气？")]}, config):
    print(chunk)
```

**人在回路（Human-in-the-loop）**，这是 LangGraph 的杀手锏：

```python
graph = builder.compile(
    checkpointer=MemorySaver(),
    interrupt_before=["tools"],     # 执行工具前暂停，等人工确认
)

# 第一次运行会停在 tools 前
graph.invoke({"messages": [("user", "给张三转账 5000 元")]}, config)

# 人工确认后，用同一个 thread_id 继续（传 None 表示接着跑）
graph.invoke(None, config)
```

### 底层逻辑

- **State + Reducer**：状态是一个 TypedDict，每个字段可以配 reducer 决定「新值如何合并旧值」（追加、覆盖、求和）。这是它能做复杂状态管理的关键。
- **Checkpointer**：每一步执行后把状态快照存到存储（内存 / SQLite / Postgres）。所以能暂停、能恢复、能回放、能改状态重跑。**这是「可中断 Agent」的技术基础**。
- **Pregel 式执行**：按 superstep 推进，同一步内并行节点一起跑，天然支持 fan-out / fan-in。
- **子图（Subgraph）**：可以把一个图当成另一个图的节点，实现模块化——这是大型项目能维护的原因。

### 优点

- **可控性最强**：每个分支、每次重试、每个人工审批点都是显式的。
- **持久化 + 断点续跑**：长任务挂了能接着跑，不丢进度。
- **可观测**：配合 LangSmith 能看到完整执行树。
- **不强制绑定 LangChain**：可以纯用它做状态机，模型调用直接写 OpenAI SDK。

### 缺点

- **学习曲线陡**：状态、reducer、checkpointer、中断、子图，概念多。
- **样板代码多**：一个简单 Agent 要写几十行，不如 Agents SDK 直接。
- **图会变复杂**：业务一多，图就成蜘蛛网，需要纪律（按子图拆分）。
- **调试需要工具**：没有 LangSmith 时，看状态流转很痛苦。

### 什么时候用

**必须用**：多步骤、有分支、需要人工审批、需要断点恢复、长时运行的生产 Agent。金融审批流、客服工单流、数据分析流水线、Coding Agent。

**不必用**：单轮问答、简单 RAG、三步以内的固定流程。

> 一句话定位：**LangGraph 是 Agent 界的「工作流引擎」**，类比 Airflow / Temporal，只不过节点里跑的是 LLM。

## 3.4 CrewAI：把 Agent 当「员工」来组织

### 它解决什么问题

让「多个角色分工协作」这件事写起来像写组织架构图：定义角色（Role）、目标（Goal）、背景（Backstory），然后组队（Crew）干活。

### 怎么调

```python
from crewai import Agent, Task, Crew, Process

researcher = Agent(
    role="资深行业研究员",
    goal="找出 {topic} 领域近三年的关键技术突破",
    backstory="你在顶级咨询公司做了十年技术尽调，擅长从噪音中筛出真信号。",
    verbose=True,
    allow_delegation=False,
)

writer = Agent(
    role="技术内容主编",
    goal="把研究结论写成 800 字、有数据支撑的简报",
    backstory="你写过上千篇技术长文，擅长把复杂概念讲得让非技术高管也能懂。",
)

task1 = Task(
    description="调研 {topic}，输出 5 条关键突破，每条附来源与时间。",
    expected_output="5 条要点，每条 50 字以内，带来源。",
    agent=researcher,
)

task2 = Task(
    description="基于研究结论写一份 800 字简报。",
    expected_output="Markdown 格式，含小标题与结论段。",
    agent=writer,
    context=[task1],          # 显式声明依赖
)

crew = Crew(
    agents=[researcher, writer],
    tasks=[task1, task2],
    process=Process.sequential,   # 也可 Process.hierarchical（有 manager 分派）
    verbose=True,
)
print(crew.kickoff(inputs={"topic": "固态电池"}))
```

### 底层逻辑

CrewAI 把每个 Agent 包装成一个「带角色提示词的 LLM 调用器」。`Task` 按 `process` 顺序或层级执行，`context` 决定哪些前序输出会进入当前任务的上下文。所谓「协作」，本质是**前一个 Agent 的输出被拼进后一个 Agent 的提示词**。

`Process.hierarchical` 会额外生成一个 manager Agent，由它决定派谁做、做几轮——这时才有一点「动态编排」的意思。

### 优点

- **概念直观**：角色/任务/团队，非技术人员也能理解。
- **上手极快**：几十行就能跑出一个多 Agent 流水线。
- **内置不少实用件**：记忆、缓存、工具、流程控制。
- **输出质量常优于单 Agent**：分工 + 上下文隔离确实能减少「一个模型什么都干」的混乱。

### 缺点

- **本质是顺序流水线**：所谓「多 Agent 协作」多为串行，不是真并行推理。
- **token 消耗大**：每个 Agent 都带自己的角色提示和历史，成本翻几倍。
- **调试困难**：出问题时不知道是哪个角色的提示词有问题。
- **可控性弱**：复杂分支、重试、人工审批支持有限，复杂了就得上 LangGraph。
- **角色提示词敏感**：backstory 写不好，Agent 就「演」不出你要的专业度。

### 什么时候用

**用**：内容生产流水线（调研→写作→审校）、多视角分析（正反方辩论）、报告生成、快速搭一个「AI 团队」Demo。

**不用**：需要精确控制流程的业务系统、延迟敏感场景、成本敏感场景。

## 3.5 AutoGen / AG2：多 Agent 对话式协作

### 它解决什么问题

让多个 Agent 通过**互相发消息**来解决问题，最典型的是「写代码的 Agent + 执行代码的 Agent + 审查的 Agent」循环对话，直到任务完成。

### 怎么调（AutoGen 0.4+ / AgentChat）

```python
import asyncio
from autogen_agentchat.agents import AssistantAgent, CodeExecutorAgent
from autogen_agentchat.teams import RoundRobinGroupChat
from autogen_agentchat.conditions import TextMentionTermination
from autogen_ext.models.openai import OpenAIChatCompletionClient
from autogen_ext.code_executors.local import LocalCommandLineCodeExecutor

async def main():
    model = OpenAIChatCompletionClient(model="gpt-4o-mini")

    coder = AssistantAgent(
        "coder", model_client=model,
        system_message="你是 Python 专家。写代码时用 ```python 代码块，写完让 executor 运行。",
    )
    reviewer = AssistantAgent(
        "reviewer", model_client=model,
        system_message="你审查代码的正确性与边界条件。通过时回复 TERMINATE。",
    )
    executor = CodeExecutorAgent(
        "executor", code_executor=LocalCommandLineCodeExecutor(work_dir="./sandbox"),
    )

    team = RoundRobinGroupChat(
        [coder, executor, reviewer],
        termination_condition=TextMentionTermination("TERMINATE"),
        max_turns=12,
    )
    result = await team.run(task="写一个函数，判断字符串是否是回文，并给出 3 个测试用例。")
    print(result.messages[-1].content)

asyncio.run(main())
```

### 底层逻辑

- **对话即协作**：每个 Agent 的输出进入共享消息列表，下一个 Agent 读全部历史再发言。这就是「群聊」模型。
- **GroupChat 选择器**：轮询（RoundRobin）、由 LLM 选下一个发言者（Selector）、或按图（Graph）走。
- **代码执行器**：AutoGen 最有价值的组件，能让模型真的跑代码并拿到结果——这是「自我纠错」闭环的关键。
- **0.4 重构**：从「可对话 Agent」重构成「actor 模型 + 消息总线」，支持分布式与跨语言，但也导致大量旧教程失效。

### 优点

- **代码执行闭环强**：写→跑→看报错→改，这个循环是它最成熟的场景。
- **研究友好**：多 Agent 辩论、群体智能实验的首选。
- **微软背书**：文档质量高，论文支撑多。

### 缺点

- **API 变动剧烈**：0.2 → 0.4 几乎重写，学习成本高。
- **token 爆炸**：群聊意味着每个 Agent 都读全部历史，轮次一多成本失控。
- **容易「聊飞」**：Agent 之间互相客气、重复、跑题，需要严格终止条件。
- **生产化不足**：状态持久化、可观测、权限控制都要自己补。

### 什么时候用

**用**：代码生成与自动修复、多 Agent 辩论式推理、科研实验、需要「执行反馈」的任务。

**不用**：面向终端用户的产品（成本与稳定性都不可控）。

## 3.6 OpenAI Agents SDK：最轻的「官方最小实现」

### 它解决什么问题

OpenAI 在 2025 年把实验性的 Swarm 升级为正式 SDK，核心只有四个概念：**Agent、Handoff（交接）、Guardrail（护栏）、Session（会话）**。它的哲学是「不要框架，只要原语」。

### 怎么调

```python
from agents import Agent, Runner, function_tool, input_guardrail, GuardrailFunctionOutput

@function_tool
def get_order_status(order_id: str) -> str:
    """根据订单号查询物流状态。order_id 形如 'SO20240101'。"""
    return f"订单 {order_id}：已发货，预计 3 天送达"

@function_tool
def refund(order_id: str, amount: float) -> str:
    """发起退款。amount 单位为元，不得超过订单金额。"""
    return f"已为订单 {order_id} 发起 {amount} 元退款"

billing = Agent(
    name="账单专员",
    instructions="你只处理退款与账单问题。金额超过 500 元必须转人工。",
    tools=[refund],
)

support = Agent(
    name="客服",
    instructions="你是电商客服。物流问题自己查，退款问题交给账单专员。",
    tools=[get_order_status],
    handoffs=[billing],          # 交接：模型可自主决定转给 billing
)

result = Runner.run_sync(support, "我的订单 SO20240101 到哪了？")
print(result.final_output)
```

流式 + 会话：

```python
from agents import SQLiteSession

session = SQLiteSession("user-123", "conversations.db")
result = Runner.run_sync(support, "我要退款", session=session)   # 自动带历史
```

### 底层逻辑

`Runner` 就是一个循环：调 Responses API → 如果返回 tool_call 就执行并回填 → 如果返回 handoff 就切换当前 Agent 继续 → 直到产出最终文本。**它把 1.4 节那个 while 循环做到了极致精简**，代码量比 LangGraph 少一个数量级。

Handoff 的实现很巧妙：把「转给某个 Agent」包装成一个特殊工具，模型调用它，运行时就把当前 Agent 换掉。

### 优点

- **极简**：四个概念覆盖 80% 场景，半天能上手。
- **默认行为合理**：自动工具循环、自动交接、内置 tracing。
- **原生支持结构化输出**（Pydantic 模型直接当 schema）。
- **代码可读性极高**，几乎等于在写业务描述。

### 缺点

- **绑定 OpenAI 生态**：虽然支持兼容端点，但 Responses API 的特性（内置工具、托管记忆）只有 OpenAI 有。
- **复杂流程表达力不足**：没有图、没有显式状态机、没有原生人工审批节点。
- **持久化弱**：Session 只解决会话历史，不是 LangGraph 那种完整状态快照。
- **生态年轻**：第三方集成少。

### 什么时候用

**用**：单 Agent + 少量工具、客服分流、任务型助手、想快速上线的产品。

**不用**：多步骤审批流、需要断点恢复的长任务。

## 3.7 Google ADK：工程化最完整的开源 Agent 框架

### 它解决什么问题

Google 2025 年开源的 Agent Development Kit，定位类似「Agent 界的 Spring」：多 Agent 层级、工作流 Agent（顺序/并行/循环）、会话状态、评测、部署一条龙，且模型无关（Gemini / Claude / 开源模型都行）。

### 怎么调

```python
from google.adk.agents import LlmAgent, SequentialAgent
from google.adk.tools import google_search

researcher = LlmAgent(
    name="researcher",
    model="gemini-2.5-flash",
    instruction="检索并总结 {topic} 的最新进展，输出 5 条要点。",
    tools=[google_search],
    output_key="research_result",       # 结果写入会话状态
)

writer = LlmAgent(
    name="writer",
    model="gemini-2.5-flash",
    instruction="基于 {research_result} 写 600 字简报，不要编造数据。",
    output_key="final_report",
)

root = SequentialAgent(name="pipeline", sub_agents=[researcher, writer])
```

```bash
adk web      # 本地起一个带调试面板的 Web UI
adk run      # 命令行跑
adk deploy   # 部署到 Cloud Run / Vertex
```

### 底层逻辑

- **层级 Agent 树**：父 Agent 可以把任务委派给子 Agent（`sub_agents`），子 Agent 有自己的工具和指令。
- **Session State**：一个共享的键值状态，`output_key` 自动把 Agent 输出写进去，`{key}` 在指令里自动替换。**这让「上一步输出喂给下一步」变成声明式的**。
- **Workflow Agents**：`SequentialAgent` / `ParallelAgent` / `LoopAgent` 是内置的确定性编排器，不消耗 LLM 决策。
- **Callbacks**：`before_model` / `after_model` / `before_tool` 等钩子，用于审计、脱敏、拦截。

### 优点

- **工程完备度最高**：会话、状态、回调、评测、部署、可视化调试全都有。
- **模型无关**：不锁死 Gemini，这点比 Agents SDK 开放。
- **多 Agent 层级清晰**：适合做「部门-团队-个人」式的组织结构。
- **A2A 协议原生支持**：跨服务 Agent 通信。

### 缺点

- **Google 生态倾向明显**：文档、示例、部署路径都偏向 GCP。
- **概念较多**：Agent / Workflow Agent / Tool / Callback / Session / Artifact，入门有门槛。
- **国内可用性**：Gemini 访问受限，需换模型（可行但要自己配）。
- **社区相对小**：中文资料少。

### 什么时候用

**用**：需要完整工程能力（状态、回调、评测、部署）的企业项目；多 Agent 层级结构；已经在用 GCP 的团队。

## 3.8 Claude Agent SDK：Coding Agent 的最强底座

### 它解决什么问题

把 Claude Code 那套「读写文件 + 执行命令 + 自我纠错」的能力开放成 SDK，让你用几十行代码造一个能真正干活的编程 Agent。

### 怎么调（Python）

```python
import anyio
from claude_agent_sdk import query, ClaudeAgentOptions

async def main():
    options = ClaudeAgentOptions(
        system_prompt="你是资深 Python 工程师，改代码前先读文件。",
        allowed_tools=["Read", "Write", "Edit", "Bash", "Glob", "Grep"],
        permission_mode="acceptEdits",     # 自动接受文件编辑
        cwd="./my-project",
        max_turns=30,
    )
    async for message in query(
        prompt="修复 tests/test_api.py 里失败的测试，并说明根因。",
        options=options,
    ):
        print(message)

anyio.run(main())
```

### 底层逻辑

它复用了 Claude Code 的 **Agent Loop + 工具集 + 权限系统**：模型看到的是「文件系统 + shell」这组通用工具，通过多轮读写执行来完成任务。关键在于**权限模式**（询问 / 自动接受编辑 / 完全放行）和**上下文压缩**（长任务自动摘要历史）。

### 优点

- **干真活的能力最强**：不是「生成代码片段」，而是真的能改仓库、跑测试、看报错、再改。
- **权限模型成熟**：细粒度控制哪些工具能用，适合放进 CI。
- **上下文管理成熟**：长任务不会因为超长而崩。

### 缺点

- **绑定 Anthropic**：必须用 Claude 模型。
- **成本高**：一个中型重构任务轻松烧掉几美元。
- **黑盒感**：内部循环不像 LangGraph 那样可拆解。

### 什么时候用

**用**：自动化代码维护、批量重构、CI 里自动修 lint/测试、内部研发效率工具。

## 3.9 Pydantic AI：类型安全优先的「反框架」

### 它解决什么问题

LangChain 被诟病最多的是「动态类型、运行时报错、IDE 不提示」。Pydantic AI 用 Pydantic 模型贯穿始终，让 Agent 的输入输出**在编译期/类型检查期就能发现问题**。

### 怎么调

```python
from pydantic import BaseModel, Field
from pydantic_ai import Agent, RunContext

class SupportDeps(BaseModel):
    customer_id: int
    db_url: str

class Reply(BaseModel):
    answer: str = Field(description="给用户的回答")
    confidence: float = Field(ge=0, le=1, description="置信度")
    need_human: bool = Field(description="是否需要转人工")

agent = Agent(
    "openai:gpt-4o-mini",
    deps_type=SupportDeps,
    output_type=Reply,               # 强类型输出，自动校验+重试
    system_prompt="你是严谨的客服，不确定就转人工。",
)

@agent.tool
async def get_orders(ctx: RunContext[SupportDeps]) -> list[dict]:
    """查询当前客户的订单列表。"""
    return await fetch_orders(ctx.deps.customer_id, ctx.deps.db_url)

result = agent.run_sync("我上周买的耳机还没到", deps=SupportDeps(customer_id=42, db_url="..."))
print(result.output.answer, result.output.confidence)
```

### 底层逻辑

- **依赖注入**：`deps` 把数据库连接、用户身份等「运行时资源」显式传进工具，不靠全局变量。
- **输出校验循环**：模型输出不符合 Pydantic schema 时，自动把校验错误喂回模型重试（默认有限次）。
- **日志即链路追踪**：`Logfire` 集成，每一步都有结构化记录。

### 优点

- **类型安全**：IDE 补全、mypy 检查、运行时校验三层保护。
- **代码极简**：没有链、没有图、没有 AgentExecutor，就是函数 + 装饰器。
- **可测试性极强**：`TestModel` / `FunctionModel` 可以不打真实 API 就测完整流程。
- **生产友好**：结构化输出稳定，重试机制内建。

### 缺点

- **生态小**：工具、集成远不如 LangChain。
- **多 Agent 编排弱**：官方定位是「单 Agent + 强类型」，复杂流程要自己写。
- **社区年轻**：中文资料少。

### 什么时候用

**用**：需要严格结构化输出的业务（表单抽取、分类、评分）、重视代码质量的团队、TypeScript 风格的 Python 项目。

## 3.10 Semantic Kernel / Microsoft Agent Framework

### 它解决什么问题

微软面向 .NET / Java / Python 的企业级方案，核心是 **Kernel（内核）+ Plugin（插件）+ Planner（规划器）**，把 LLM 能力做成「可注入的服务」，方便塞进已有企业系统。

### 怎么调（Python）

```python
import asyncio
from semantic_kernel import Kernel
from semantic_kernel.connectors.ai.open_ai import OpenAIChatCompletion
from semantic_kernel.functions import kernel_function

class WeatherPlugin:
    @kernel_function(description="查询城市天气")
    def get_weather(self, city: str) -> str:
        return f"{city}：晴，18℃"

async def main():
    kernel = Kernel()
    kernel.add_service(OpenAIChatCompletion(ai_model_id="gpt-4o-mini"))
    kernel.add_plugin(WeatherPlugin(), plugin_name="weather")

    result = await kernel.invoke_prompt("北京天气如何？用一句话回答。")
    print(result)

asyncio.run(main())
```

### 底层逻辑

- **Kernel 是 DI 容器**：模型、记忆、插件都注册进去，按需解析。
- **Plugin 是函数集合**：用装饰器标注描述，自动生成 function schema 给模型。
- **Planner**：让模型自动选择「调哪些插件、按什么顺序」，是早期「自动编排」的尝试。
- **2025 年后**：微软把 Semantic Kernel 与 AutoGen 合并为 **Microsoft Agent Framework**，统一了编排（图）与多 Agent 对话两种范式。

### 优点

- **企业集成强**：.NET 生态、Azure 原生、合规性好。
- **多语言**：C# / Java / Python 同一套概念。
- **稳定**：微软长期维护，API 变更比 LangChain 温和。

### 缺点

- **概念偏企业**：Kernel / Plugin / Planner，学习成本不低。
- **社区热度不如 LangChain**：第三方示例少。
- **Python 侧不如 C# 侧成熟**。

### 什么时候用

**用**：.NET 技术栈的公司、Azure 生态、需要与企业现有系统深度集成。

## 3.11 LlamaIndex：数据密集型 RAG 的王者

### 它解决什么问题

LangChain 什么都能做但都不深，LlamaIndex 专攻「把你的数据变成可查询的知识」。它的抽象是 **Index（索引）+ Retriever（检索器）+ QueryEngine（查询引擎）**。

### 怎么调

```python
from llama_index.core import VectorStoreIndex, SimpleDirectoryReader, Settings
from llama_index.llms.openai import OpenAI
from llama_index.embeddings.openai import OpenAIEmbedding

Settings.llm = OpenAI(model="gpt-4o-mini")
Settings.embed_model = OpenAIEmbedding(model="text-embedding-3-small")

docs = SimpleDirectoryReader("./data").load_data()
index = VectorStoreIndex.from_documents(docs)

# 基础问答
engine = index.as_query_engine(similarity_top_k=4)
print(engine.query("我们的退款政策是什么？"))

# 带引用的问答（生产必须）
engine = index.as_query_engine(
    similarity_top_k=6,
    response_mode="compact",
)
resp = engine.query("退款期限是几天？")
for node in resp.source_nodes:
    print(node.metadata.get("file_name"), node.score)
```

进阶：路由 + 子问题拆解

```python
from llama_index.core.query_engine import RouterQueryEngine
from llama_index.core.tool import QueryEngineTool
from llama_index.core.selectors import LLMSingleSelector

tools = [
    QueryEngineTool.from_defaults(query_engine=policy_engine, name="policy",
                                  description="公司制度与政策文档"),
    QueryEngineTool.from_defaults(query_engine=product_engine, name="product",
                                  description="产品手册与技术文档"),
]
router = RouterQueryEngine(selector=LLMSingleSelector.from_defaults(), query_engine_tools=tools)
```

### 底层逻辑

- **Node 是核心数据结构**：一段文本 + 元数据 + 关系（前后文、父子、引用），比纯 chunk 表达力强得多。
- **索引类型**：向量索引（语义）、关键词索引（精确）、树索引（层级摘要）、知识图谱索引（实体关系）。
- **检索后处理链**：召回 → 重排 → 相似度截断 → 元数据过滤 → 上下文扩展（把命中的小 chunk 换成它所在的大段落）。**最后这一步是效果提升的隐藏关键**。

### 优点

- **RAG 能力最深**：各种索引、检索策略、后处理开箱即用。
- **文档解析强**：PDF、Word、PPT、网页、数据库都有 loader。
- **评测工具**：内置检索质量与回答质量评测。
- **Agent 能力够用**：`FunctionAgent` / `ReActAgent` 也能做工具调用。

### 缺点

- **非 RAG 场景偏重**：做纯工具调用 Agent 不如 Agents SDK 直接。
- **抽象也不少**：Index / Node / Retriever / QueryEngine / Postprocessor，概念多。
- **版本迭代快**：0.10 → 0.11+ 有破坏性变更。

### 什么时候用

**用**：企业知识库、文档问答、合同审查、技术手册检索——**只要你的核心是「让模型读懂我的资料」，首选它**。

## 3.12 Dify：低代码平台里的「全能选手」

### 它解决什么问题

把「模型接入 + 提示词编排 + 知识库 + 工作流 + 发布成 API/网页」全部做成可视化，让不会写代码的人也能上线一个 AI 应用。

### 怎么用

1. **接入模型**：设置 → 模型供应商 → 填 API Key（支持 OpenAI 兼容协议，所以 vLLM / Ollama / DeepSeek 都能接）。
2. **建知识库**：上传文档 → 选分段策略 → 选 embedding 模型 → 等待索引完成。
3. **建应用**，四种类型：
   - **聊天助手**：最简，一问一答。
   - **文本生成**：单次输入输出，适合批量处理。
   - **Agent**：模型自主调用工具（内置搜索、代码执行、自定义 API）。
   - **工作流（Chatflow / Workflow）**：可视化 DAG，节点有 LLM、知识检索、条件分支、代码、HTTP 请求、循环、变量聚合。
4. **发布**：一键生成 Web App / 嵌入代码 / REST API。

调用它发布的 API：

```bash
curl -X POST 'http://localhost/v1/chat-messages' \
  -H 'Authorization: Bearer app-xxxxxxxx' \
  -H 'Content-Type: application/json' \
  -d '{
    "inputs": {},
    "query": "退款政策是什么？",
    "response_mode": "streaming",
    "conversation_id": "",
    "user": "user-001"
  }'
```

### 底层逻辑

Dify 的工作流引擎本质是一个 **DAG 执行器**：节点是算子（LLM 调用、检索、代码、HTTP），边是数据流，变量在节点间传递。它自己用 Python（Flask + Celery）实现，知识库用向量库（默认 Weaviate/Qdrant），模型层走统一适配器。

**它把 3.3 节的 LangGraph 干的事做成了画布**，代价是灵活性受限。

### 优点

- **快**：半小时能上线一个可用的 RAG 应用。
- **全**：模型、知识库、工作流、日志、标注、API 一站式。
- **可私有化**：Docker Compose 一键部署，数据不出内网。
- **开源可改**：Apache 2.0 修改版（有商用限制条款，需看清）。
- **非技术人员友好**：运营、产品能自己改提示词和流程。

### 缺点

- **复杂逻辑表达受限**：画布一复杂就难以维护，版本管理弱。
- **性能与并发**：单机部署撑不住高并发，需要自己做集群。
- **深度定制难**：想改核心逻辑要读它的源码，耦合较重。
- **升级风险**：大版本升级常有不兼容，生产环境要谨慎。
- **商用条款**：多租户 SaaS 场景有额外限制，法务要过一遍。

### 什么时候用

**用**：内部工具、快速验证、业务方自助搭建、中小团队没有专职 AI 工程师。

**不用**：高并发 C 端产品、需要深度定制的核心业务、强合规审计场景（除非自己加固）。

## 3.13 n8n：自动化流程 + AI 节点

### 它解决什么问题

n8n 本来是 Zapier 的开源替代（几百个 SaaS 集成），加了 AI 节点后变成「能让 AI 参与业务流程自动化」的平台。

### 怎么用

典型节点链：`Webhook 触发 → HTTP 请求取数据 → AI Agent 节点（带工具）→ 条件判断 → 写回 CRM / 发飞书`。

它支持 **AI Agent 节点 + 工具子节点**（HTTP Request Tool、Code Tool、Vector Store Tool），本质是把 LangChain 的 Agent 封装成节点。

### 优点

- **集成最多**：几百个 SaaS 连接器，这是 Dify 比不了的。
- **自动化能力强**：定时、Webhook、重试、错误分支都很成熟。
- **自托管友好**：Docker 部署，社区版免费。

### 缺点

- **AI 能力不如 Dify 深**：知识库、RAG 的精细度弱。
- **可视化复杂后难维护**：大流程节点上百个，排查困难。
- **不是为 AI 设计的**：AI 是「加进来的能力」，不是原生核心。

### 什么时候用

**用**：把 AI 嵌进现有业务流程（CRM 自动跟进、工单自动分类、日报自动生成）。

## 3.14 Coze / 扣子：字节的 Bot 平台

**定位**：面向 C 端和轻应用的 Bot 搭建平台，插件生态丰富（搜索、图片、文档、抖音数据），发布渠道多（飞书、微信、网页、API）。

**优点**：上手最快，插件现成，国内访问稳定，免费额度大。

**缺点**：深度定制弱、数据在平台侧、复杂逻辑受限、导出能力差（锁定风险）。

**什么时候用**：快速做个人 Bot、社群运营工具、验证想法。**不适合**核心业务系统。

## 3.15 FastGPT / RAGFlow：知识库专精

| 维度 | FastGPT | RAGFlow |
| --- | --- | --- |
| 定位 | 知识库 + 工作流，偏应用 | 深度文档理解，偏检索质量 |
| 文档解析 | 常规（PDF/Word/Markdown） | **强项**：版面分析、表格、扫描件 OCR |
| 检索 | 向量 + 混合 + 重排 | 多路召回 + 精细切分 + 可视化引用 |
| 工作流 | 有，较完整 | 较弱 |
| 部署 | Docker Compose，轻 | 较重（依赖 ES / MinIO / Redis） |
| 适合 | 客服知识库、企业内部问答 | 合同、财报、论文、手册等高精度场景 |

**一句话**：要「应用完整」选 FastGPT，要「解析和检索准」选 RAGFlow，两个也可以组合（RAGFlow 做检索层，FastGPT/Dify 做应用层）。

## 3.17 选型矩阵：一张表做决定

| 你的情况 | 首选 | 备选 | 别用 |
| --- | --- | --- | --- |
| 完全不会代码，要上线一个问答机器人 | Dify | Coze、FastGPT | LangGraph |
| 会一点 Python，做内部工具 | Dify + 少量脚本 | n8n | AutoGen |
| 企业知识库，文档多且杂 | RAGFlow（解析）+ Dify（应用） | LlamaIndex | 纯向量库裸写 |
| 生产级复杂 Agent，要审批/断点 | **LangGraph** | Google ADK | CrewAI |
| 快速做多角色内容流水线 | CrewAI | AutoGen | LangGraph（太重） |
| 单 Agent + 工具，快速上线 | **OpenAI Agents SDK** | Pydantic AI | LangChain AgentExecutor |
| 强类型、要测试、要稳定输出 | **Pydantic AI** | Instructor + 裸 SDK | CrewAI |
| 自动改代码 / CI 自动修复 | Claude Agent SDK | OpenHands、Aider | Dify |
| .NET / Azure 企业栈 | Semantic Kernel | Microsoft Agent Framework | LangChain |
| 只做 RAG，别的不需要 | LlamaIndex | Haystack | AutoGen |
| 要把 AI 接进现有 SaaS 流程 | n8n | Dify 工作流 | CrewAI |

### 三条硬建议

1. **先裸写，再上框架**。用 OpenAI SDK 手写一遍那个 while 循环（1.4 节），你会立刻明白框架在替你做什么，也才知道该不该用。
2. **生产环境优先选「约束多、魔法少」的**：LangGraph、Pydantic AI、Agents SDK 都属于「行为可预测」的一类；CrewAI、AutoGen 属于「行为涌现」的一类，适合探索不适合交付。
3. **一个项目只用一套编排**。混用两套框架（比如 Dify 调 LangGraph 服务）可以做，但要把边界划在 HTTP 接口上，不要让两套状态互相纠缠。
