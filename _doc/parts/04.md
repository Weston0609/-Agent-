# 第四章 框架之间怎么联系：协议层与企业真实架构

前面一章把框架当成独立个体看了。但真实系统里，它们不是并列的，而是**分层的**。这一章讲清「谁调谁、靠什么调」，以及你进公司后会看到的真实架构长什么样。

## 4.1 一张图看清所有框架的层级关系

```text
┌──────────────────────────────────────────────────────────┐
│  交互层   Web / App / 飞书 / 微信 / 语音 / IDE 插件        │
├──────────────────────────────────────────────────────────┤
│  应用层   Dify / Coze / FastGPT / 自研前端                 │
├──────────────────────────────────────────────────────────┤
│  编排层   LangGraph / CrewAI / Agents SDK / ADK / 自研     │
│           （低代码平台的「工作流」也在这层）                 │
├──────────────────────────────────────────────────────────┤
│  协议层   OpenAI 兼容 API │ MCP │ A2A │ OpenAPI │ gRPC     │
├──────────────────────────────────────────────────────────┤
│  能力层   模型推理 │ 向量检索 │ 工具服务 │ 记忆 │ 沙箱      │
├──────────────────────────────────────────────────────────┤
│  基础设施 GPU / K8s / 对象存储 / 消息队列 / 监控            │
└──────────────────────────────────────────────────────────┘
```

**三条关键洞察**：

1. **上层通过协议调下层，而不是通过代码 import**。Dify 调模型走 HTTP，LangGraph 调工具走 MCP，跨服务 Agent 走 A2A。**协议是解耦点**。
2. **同一层可以替换，只要协议不变**。今天用 Dify 做应用，明天换自研前端，只要都调同一个后端 API，下层不用动。
3. **框架的「联系」本质是数据格式的约定**。所谓集成，就是「A 的输出能变成 B 的输入」。

## 4.2 协议层详解（这是最容易忽略、但最重要的一层）

### 4.2.1 OpenAI 兼容协议：事实上的「模型界 HTTP」

**它是什么**：一套 REST 接口约定，最核心三个端点：

| 端点 | 用途 |
| --- | --- |
| `POST /v1/chat/completions` | 对话补全（最常用） |
| `POST /v1/embeddings` | 文本向量化 |
| `GET /v1/models` | 列出可用模型 |

**为什么它成了标准**：因为几乎所有工具（LangChain、Dify、LlamaIndex、网关）都只实现这一套。**只要你的服务兼容它，就能被整个生态直接使用**——这是 vLLM、Ollama、DeepSeek、通义、智谱全都提供 `/v1` 端点的原因。

**请求结构**（记住这五个字段就够用）：

```json
{
  "model": "qwen2.5-7b",
  "messages": [
    {"role": "system", "content": "你是助手"},
    {"role": "user", "content": "你好"},
    {"role": "assistant", "content": "你好，有什么可以帮你？"},
    {"role": "tool", "tool_call_id": "call_1", "content": "{\"temp\": 18}"}
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "查询城市天气",
        "parameters": {
          "type": "object",
          "properties": {"city": {"type": "string", "description": "城市名"}},
          "required": ["city"]
        }
      }
    }
  ],
  "temperature": 0.3,
  "stream": true
}
```

**流式响应**是 SSE（Server-Sent Events），每行 `data: {...}`，以 `data: [DONE]` 结束。增量内容在 `choices[0].delta.content`，工具调用在 `choices[0].delta.tool_calls`（注意：分片到达，需要按 `index` 拼接）。

### 4.2.2 MCP（Model Context Protocol）：工具界的 USB-C

**它是什么**：Anthropic 2024 年底提出的开放协议，用统一方式把「工具、数据、提示词」暴露给任何 LLM 应用。解决的是 **M×N 问题**：M 个 AI 应用 × N 个数据源，没有协议要写 M×N 个适配器，有了协议只需 M+N 个。

```text
没有 MCP：  App1─┐ App2─┐ App3─┐
                  ├──┬──┼──┬───┤        每个 App 对每个数据源写一套
            DB ───┘  │  │  │   │
            Git ─────┘  │  │   │
            Slack ──────┘  │   │
            Files ─────────┘   │
                                │
有 MCP：    App1  App2  App3
              \    |    /
               \   |   /             都只说 MCP
            ┌───┴───┴───┴───┐
            │  MCP Servers  │
            └───┬───┬───┬───┘
               DB  Git Slack
```

**架构三角**：

| 角色 | 是什么 | 例子 |
| --- | --- | --- |
| Host（宿主） | 用户面对的 AI 应用 | Claude Desktop、Cursor、你的 Agent 程序 |
| Client（客户端） | Host 内部的连接器，一个 client 连一个 server | SDK 里的 `ClientSession` |
| Server（服务端） | 暴露能力的程序 | 文件系统服务、数据库服务、你写的业务服务 |

**Server 提供三类原语**：

| 原语 | 谁控制 | 用途 | 例子 |
| --- | --- | --- | --- |
| Tools | 模型决定调用 | 执行动作 | 查订单、发邮件、跑 SQL |
| Resources | 应用决定读取 | 提供数据 | 文件内容、数据库表结构 |
| Prompts | 用户主动选择 | 预设提示模板 | 「代码审查」模板 |

**传输方式**：

- **stdio**：本地进程，Host 启动 Server 子进程，通过标准输入输出通信。简单、无需网络、最安全。
- **Streamable HTTP**：远程服务，POST + 可选 SSE 流。用于多用户、云端部署。

**2026 年规范的重大变化**（必须知道，否则看的教程会过时）：

1. **移除协议级会话**：不再有 `initialize` 握手和 `Mcp-Session-Id` 头。每个请求自带 `_meta` 里的协议版本与客户端能力，**MCP 变成无状态协议**。跨调用状态要用服务端自己签发的 handle 当普通参数传。
2. **新增 `server/discover`**：服务端必须实现，用来宣告自己支持的版本、能力和身份。客户端可以先探测再选版本。
3. **`subscriptions/listen` 取代 HTTP GET 与 `resources/subscribe`**：一条长连接流统一接收变更通知。
4. **移除 `ping`、`logging/setLevel`**：日志级别改为每个请求在 `_meta` 里带 `io.modelcontextprotocol/logLevel`。
5. **MRTR（多轮请求）模式**：服务端不再主动发请求（sampling / elicitation / roots/list），改为返回 `resultType: "input_required"` 让客户端补齐信息后重试原请求。
6. **所有结果必须带 `resultType`**：`"complete"` 或 `"input_required"`。
7. **列表结果必须带 `ttlMs` 和 `cacheScope`**：支持客户端缓存，降低轮询。
8. **Roots / Sampling / Logging 被标记为废弃**：新实现不要再用。Sampling 的替代方案是「服务端自己直连模型 API」。
9. **Streamable HTTP 要求 `Mcp-Method` / `Mcp-Name` 头**，便于网关路由与审计。
10. **移除 SSE 断线重连**（`Last-Event-ID`）：流断了就重新发请求。

> 这些变化的方向很明确：**让 MCP 更像普通 HTTP 服务**——无状态、可缓存、可被网关代理、可水平扩展。这对企业部署是巨大利好。

### 4.2.3 A2A（Agent to Agent）：Agent 之间的电话线

MCP 解决「Agent 调工具」，A2A 解决「Agent 调 Agent」。核心概念是 **Agent Card**（一个 `.well-known/agent.json` 文件，描述这个 Agent 能干什么、怎么调），任务通过 `tasks/send` 提交，支持长任务与流式更新。

**什么时候真需要 A2A**：跨团队、跨公司、跨技术栈的 Agent 协作。**什么时候不需要**：你自己系统内的两个 Agent，直接函数调用或 HTTP 就行，别为了「架构先进」引入协议开销。

### 4.2.4 OpenAPI / gRPC：老协议的新用途

- **OpenAPI**：把已有 REST 服务自动转成工具（很多框架支持「给一个 swagger.json 就生成工具集」）。企业里大量存量系统是 REST，这是最低成本的接入方式。
- **gRPC**：内部高性能服务间调用，适合模型推理服务、特征服务。不适合直接暴露给 LLM（schema 太复杂）。

## 4.3 你进公司后会看到的四种真实架构

### 架构一：SaaS 快速验证型（中小团队、内部工具）

```text
用户 → Dify（工作流 + 知识库）→ 模型 API（DeepSeek / 通义）
                    ↓
              向量库（Dify 内置）
```

**特征**：1～2 人维护，Docker Compose 部署在一台 8 核 32G 服务器上，月成本几百到几千元。

**你会做的事**：配模型、调提示词、传文档、画流程、看日志。

**天花板**：并发上不去，复杂逻辑做不了，数据量大就卡。

### 架构二：自研 Agent 服务型（有研发团队的产品公司）

```text
前端 → API 网关（鉴权/限流）
        ↓
     业务服务（FastAPI / Go）
        ↓
     编排层（LangGraph，跑在 K8s）
        ├─→ 模型网关（LiteLLM）→ 多个模型供应商
        ├─→ 向量库（Milvus / Qdrant / pgvector）
        ├─→ MCP 工具服务（订单/CRM/工单）
        └─→ 记忆存储（Redis + Postgres）
        ↓
     可观测（LangSmith / Langfuse + Prometheus + Grafana）
```

**特征**：5～30 人团队，K8s 部署，有 CI/CD，有灰度，有成本看板。

**你会做的事**：写节点、设计状态、接工具、调提示词、看 trace、压测、优化成本。

**这是最典型的「AI 工程师」岗位场景**。

### 架构三：私有化大模型平台型（金融 / 政企 / 医疗）

```text
内网用户 → 统一 AI 门户（自研 or Dify 企业版）
             ↓
         模型网关（OneAPI / LiteLLM，带审计）
             ↓
         vLLM 集群（多卡，Qwen / DeepSeek 量化版）
             ↓
     GPU 调度（K8s + device plugin / 昇腾）
             ↓
     数据层：向量库 + 对象存储 + 知识库（全内网）
```

**特征**：数据绝对不出内网，全栈信创适配（麒麟 OS + 昇腾/海光 + 达梦/人大金仓），有等保三级要求。

**你会做的事**：模型部署调优、推理性能压测、国产硬件适配、安全加固、审计日志。

**这是「AI 平台工程师」岗位场景，也是目前国内需求量最大的一类。**

### 架构四：Coding Agent 型（研发效能团队）

```text
开发者 → IDE 插件 / PR 评论
           ↓
      Coding Agent 服务（Claude Agent SDK / OpenHands）
           ├─→ 代码检索（向量 + AST）
           ├─→ 沙箱执行（Docker / Firecracker）
           ├─→ CI 系统（跑测试）
           └─→ Git 服务（提 PR）
```

**特征**：内部工具，用户是工程师，容忍度高但对质量要求也高。

**你会做的事**：工具设计、沙箱安全、上下文压缩策略、评测集建设。

## 4.4 各层之间的「接口契约」清单

做架构设计时，把这些契约定死，后面换组件就不痛：

| 边界 | 契约 | 换组件时改什么 |
| --- | --- | --- |
| 应用 ↔ 编排 | HTTP/JSON，定义好请求响应 schema | 只改编排服务 |
| 编排 ↔ 模型 | OpenAI 兼容协议 + 统一 model 名 | 只改网关配置 |
| 编排 ↔ 工具 | MCP（推荐）或 OpenAPI | 只改 MCP 配置 |
| 编排 ↔ 检索 | 统一 `retrieve(query, top_k) -> [chunk]` 接口 | 只改检索适配器 |
| 编排 ↔ 记忆 | `get(user_id) / append(user_id, msg)` | 只改存储实现 |
| 服务 ↔ 观测 | OpenTelemetry（trace_id 贯穿） | 不用改 |

> 一条铁律：**不要让你的业务代码 import 具体框架的类型**。定义自己的 `LLMClient` / `ToolRegistry` 接口，框架只作为实现。这样换框架是「换实现」，不是「重写业务」。这是所有能活过两年的 AI 项目的共同点。

## 4.5 框架组合的四种正确姿势

**姿势一：低代码做前台，代码做后台**

```text
Dify 工作流（业务方自己改）→ HTTP 节点 → 自研 FastAPI 服务（复杂逻辑）
```

好处：业务方能自助调整，复杂逻辑仍在工程掌控内。**这是中小团队性价比最高的组合。**

**姿势二：LangGraph 做编排，Agents SDK 做子 Agent**

```python
# LangGraph 节点内部调用一个用 Agents SDK 写的子 Agent
async def research_node(state):
    result = Runner.run_sync(research_agent, state["query"])
    return {"findings": result.final_output}
```

好处：主流程可控（图），子任务灵活（轻量 SDK）。

**姿势三：LlamaIndex 做检索层，任何框架做编排层**

把 LlamaIndex 包成一个 MCP Server 或一个 HTTP 接口，暴露 `search_knowledge(query)` 工具。这样编排框架换成什么都不影响知识库。

**姿势四：n8n 做触发器，Agent 做决策**

```text
定时/Webhook（n8n）→ 调用 Agent API → 结果写回 CRM / 发通知
```

好处：复用 n8n 的几百个连接器，不用自己写集成。

## 4.6 反模式：四种会害死项目的组合

| 反模式 | 为什么错 | 正确做法 |
| --- | --- | --- |
| LangChain + LangGraph + LlamaIndex 全上 | 三套抽象叠在一起，报错栈三层深，没人能调 | 只留一套编排 + 一套检索 |
| 每个业务线各建一个 Dify | 模型 Key 分散、知识库重复、无法统一审计 | 统一平台 + 多工作空间 |
| 用 CrewAI 做需要审批的金融流程 | 流程不可控，无法保证「必须人工确认」 | LangGraph + interrupt |
| 直接把模型 API Key 写在前端 | Key 泄露，一夜之间被盗刷上万 | 后端代理 + 网关 + 限额 |
