# 第九章 淘汰与迁移：三年后你该用什么

技术选型最怕的不是「选错」，是「选了一个三年后没人维护的」。这一章讲怎么判断什么会死、什么会活，以及死了怎么迁移。

## 9.1 先看清一个事实：框架在快速洗牌

回顾过去三年（2023—2026）的真实情况：

| 时间 | 当时的主流 | 现在的状态 |
| --- | --- | --- |
| 2023 上半年 | LangChain 一统天下 | 仍在，但核心价值被 LangGraph 接走 |
| 2023 下半年 | AutoGPT / BabyAGI 热潮 | 基本消亡，思想被吸收 |
| 2023 末 | 各种 "Agent 平台" 涌现 | 90% 已死 |
| 2024 | RAG 框架大战（LlamaIndex / Haystack / RAGFlow） | 分化：LlamaIndex 退守数据层，RAGFlow 做产品 |
| 2024 末 | AutoGen / CrewAI 多智能体 | AutoGen 被 Microsoft Agent Framework 取代 |
| 2025 | MCP 成为协议标准 | 事实标准，且已被各大厂采纳 |
| 2025 末 | OpenAI Agents SDK / Claude Agent SDK | 成为「原生 SDK 派」主流 |
| 2026 | Agent 框架收敛为三类：原生 SDK / 图编排 / 低代码平台 | 格局基本稳定 |

**规律**：**抽象层越高，死得越快。** 因为高抽象层试图「替你决定」，而模型能力每半年变一次，替你做的决定很快就过时了。

**活得久的**：协议（HTTP、OpenAI 兼容、MCP）、底层引擎（vLLM、llama.cpp）、基础设施（Docker、K8s、Postgres、Redis）。

**死得快的**：重度封装的「一键 Agent」、绑定特定模型的 DSL、可视化但不可导出的平台。

## 9.2 判断一个框架会不会死：七个信号

| 信号 | 危险程度 | 说明 |
| --- | --- | --- |
| 核心维护者离职 / 转去别的项目 | 🔴 高 | 开源项目的命脉是人 |
| 最近 6 个月无实质提交（只有依赖升级） | 🔴 高 | 已经进入维护模式 |
| Issue 积压超过 500 且无人回应 | 🟠 中高 | 社区信心在流失 |
| 被商业公司收购后改变许可证 | 🟠 中高 | 典型如 HashiCorp 系 |
| 官方文档停止更新，示例跑不通 | 🟠 中高 | 实际已放弃 |
| 只支持单一模型厂商 | 🟡 中 | 厂商策略一变就死 |
| 生态里没有第三方插件/集成 | 🟡 中 | 没有网络效应 |
| Star 增长停滞但 Fork 增长 | 🟡 中 | 大家在分叉自救 |

**反过来，健康的信号**：
- 有明确的 RFC 流程和版本路线图
- 有多家公司贡献（不是一言堂）
- 有生产案例公开（不是只有 demo）
- 破坏性变更遵循语义化版本
- 有商业支持或基金会托管

**实操建议**：选框架前，去 GitHub 看 **最近 90 天的 commit 频率、issue 响应时间、release 节奏**。这三个数比 Star 数有用一百倍。

## 9.3 各类框架的「淘汰预测」与替代方案

> 以下是基于当前趋势的判断，不是预言。技术变化快，请以你实际调研为准。

### Agent 编排框架

| 框架 | 判断 | 理由 | 替代方案 |
| --- | --- | --- | --- |
| **LangGraph** | 🟢 中期安全 | 图编排是刚需，且已被大量生产验证；LangChain 生态支撑 | 若死，迁 LangGraph 思路到自研状态机 |
| **OpenAI Agents SDK** | 🟢 安全 | 官方维护，协议级支持 MCP | 迁 Claude Agent SDK / Pydantic AI |
| **Claude Agent SDK** | 🟢 安全 | Anthropic 官方，Coding Agent 事实标准 | 同上 |
| **Pydantic AI** | 🟢 安全 | 类型安全路线，依赖少，社区健康 | 迁原生 SDK |
| **Google ADK** | 🟡 观望 | 绑定 GCP 生态，国内可用性差 | 迁 LangGraph |
| **CrewAI** | 🟠 中风险 | 角色抽象好用但天花板低，复杂场景要绕 | 迁 LangGraph |
| **AutoGen / AG2** | 🔴 已被取代 | Microsoft 已转向 Agent Framework | 迁 Microsoft Agent Framework 或 LangGraph |
| **Semantic Kernel** | 🟠 中风险 | 被 Agent Framework 吸收 | 迁 Microsoft Agent Framework |
| **LlamaIndex（Agent 部分）** | 🟡 分化 | 重心退守数据/RAG 层 | Agent 部分迁 LangGraph，数据部分可留 |
| **Haystack** | 🟢 相对安全 | deepset 商业支持，企业级 RAG 稳定 | 可继续用 |
| **smolagents** | 🟡 实验性 | HuggingFace 出品，轻量，但定位是研究 | 生产迁 Pydantic AI |

### 低代码平台

| 平台 | 判断 | 理由 |
| --- | --- | --- |
| **Dify** | 🟢 安全 | 开源可自部署，社区活跃，企业采用广 |
| **n8n** | 🟢 安全 | 自动化领域的老牌，AI 只是新增能力 |
| **Coze（扣子）** | 🟡 观望 | 字节生态内好用，但平台锁定风险 |
| **FastGPT** | 🟡 观望 | 国内 RAG 场景好用，但功能被 Dify 覆盖 |
| **RAGFlow** | 🟢 相对安全 | 文档解析是硬壁垒，短期难替代 |
| **Langflow** | 🟡 观望 | 可视化 LangChain，随 LangChain 起落 |

### 协议与标准（最值得押注）

| 标准 | 判断 | 说明 |
| --- | --- | --- |
| **OpenAI 兼容 API** | 🟢 事实标准 | 几乎所有模型/引擎都支持，短期不会变 |
| **MCP** | 🟢 事实标准 | 已被 OpenAI/Google/微软采纳，且 2026 版在向「普通 HTTP 服务」收敛 |
| **A2A** | 🟡 早期 | Agent 间通信，Google 主导，采纳度待观察 |
| **OpenTelemetry（LLM 语义约定）** | 🟢 安全 | 可观测性的通用标准 |

**结论：押注协议，不要押注框架。** 协议是共识，框架是意见。

## 9.4 什么样的架构能「抗淘汰」

这是本章最重要的部分。答案是：**把易变的部分隔离在边界内**。

### 抗淘汰架构的四条原则

**原则 1：核心逻辑与框架解耦**

```python
# ❌ 差：业务逻辑长在框架里，换框架等于重写
from langchain.agents import AgentExecutor
def build():
    return AgentExecutor(agent=..., tools=..., memory=...)

# ✅ 好：业务逻辑是纯函数，框架只是外壳
def decide_next_action(state: AgentState, llm: LLMClient) -> Action:
    """纯业务逻辑，不依赖任何框架"""
    ...

# 框架适配层（薄薄一层，换框架只改这里）
class LangGraphRunner:
    def run(self, state): return graph.invoke(state)
class NativeRunner:
    def run(self, state): ...
```

**原则 2：模型访问统一走一个客户端**

```python
# 所有地方都通过这一个入口，换模型只改配置
class LLMClient:
    def __init__(self, base_url, api_key, model): ...
    def chat(self, messages, **kw) -> str: ...
    def stream(self, messages, **kw) -> Iterator[str]: ...
    def tool_call(self, messages, tools) -> ToolCall: ...
```

**原则 3：工具用 MCP 或 OpenAPI 描述，不写死在框架里**

工具是「能力」，不是「框架的一部分」。用 MCP Server 暴露，任何框架都能接。这样换框架时工具层零改动。

**原则 4：状态与存储用通用格式**

```text
❌ 用框架私有格式存对话历史 → 换框架数据迁移地狱
✅ 用标准 JSON 存 messages 数组 → 任何框架都能读
❌ 用框架私有向量库封装 → 换框架要重灌
✅ 直接用 Qdrant/Milvus/pgvector 的 SDK → 通用
```

### 一个抗淘汰的分层示意

```text
┌─────────────────────────────────────────────┐
│  业务逻辑层（纯 Python，无框架依赖）          │  ← 最稳定，永不需要重写
│  决策规则、业务流程、领域模型                  │
├─────────────────────────────────────────────┤
│  适配层（薄，可替换）                         │  ← 换框架只改这里
│  Runner / Adapter / 框架封装                  │
├─────────────────────────────────────────────┤
│  协议层（标准）                               │  ← 押注这里
│  OpenAI 兼容 API / MCP / OpenTelemetry        │
├─────────────────────────────────────────────┤
│  基础设施层（稳定）                           │  ← 十年不变
│  vLLM / Postgres / Redis / Qdrant / K8s      │
└─────────────────────────────────────────────┘
```

**核心思想**：让「会变的东西」尽量薄、尽量靠上；让「不变的东西」尽量厚、尽量靠下。

## 9.5 迁移实战：从 LangChain AgentExecutor 迁到原生实现

这是一个真实会发生的迁移。假设你有一个 2023 年写的 LangChain Agent：

```python
# 旧代码（LangChain 0.1 时代）
from langchain.agents import initialize_agent, Tool
from langchain.agents import AgentType
from langchain.chat_models import ChatOpenAI

tools = [
    Tool(name="search", func=search_fn, description="搜索知识库"),
    Tool(name="calc", func=calc_fn, description="计算"),
]
agent = initialize_agent(
    tools, ChatOpenAI(model="gpt-3.5-turbo"),
    agent=AgentType.OPENAI_FUNCTIONS, verbose=True,
)
result = agent.run("帮我查一下退款政策并算出 7 天后的日期")
```

**迁移步骤**：

**第 1 步：把工具抽成 MCP Server（一次性投入，永久受益）**

```python
# tools_server.py
from mcp.server.fastmcp import FastMCP
from pydantic import BaseModel, Field

mcp = FastMCP("business-tools")

class SearchInput(BaseModel):
    query: str = Field(..., min_length=1, max_length=500)

@mcp.tool()
def search(inp: SearchInput) -> str:
    """搜索企业知识库，返回最相关的 3 条内容"""
    return do_search(inp.query)

class CalcInput(BaseModel):
    expr: str = Field(..., pattern=r"^[0-9+\-*/(). ]+$")

@mcp.tool()
def calc(inp: CalcInput) -> str:
    """执行四则运算，输入必须是合法数学表达式"""
    return str(eval(inp.expr))   # 注意：已用正则限制字符集

if __name__ == "__main__":
    mcp.run(transport="streamable-http")
```

**第 2 步：写原生 Agent 循环（30 行，零框架依赖）**

```python
import json
from llm_client import LLMClient

def run_agent(question: str, llm: LLMClient, tools: dict, max_steps=8) -> str:
    messages = [
        {"role": "system", "content": "你可以调用工具。需要信息时调用工具，不要编造。"},
        {"role": "user", "content": question},
    ]
    for step in range(max_steps):
        resp = llm.chat(messages, tools=[t.schema for t in tools.values()])
        if not resp.tool_calls:
            return resp.content

        messages.append({"role": "assistant", "content": resp.content or "",
                         "tool_calls": resp.tool_calls})
        for tc in resp.tool_calls:
            fn = tools.get(tc.name)
            try:
                result = fn.run(**json.loads(tc.arguments)) if fn else "未知工具"
            except Exception as e:
                result = f"工具执行失败: {e}"
            messages.append({"role": "tool", "tool_call_id": tc.id,
                             "content": str(result)[:4000]})
    return "达到最大步数，未能完成"
```

**第 3 步：写迁移前后的对比测试（保证行为一致）**

```python
CASES = [
    ("帮我查一下退款政策", ["search"]),
    ("7 天后的日期是多少", ["calc"]),
    ("帮我查退款政策并算 7 天后", ["search", "calc"]),
]

for q, expect_tools in CASES:
    out = run_agent(q, llm, tools)
    used = extract_tool_names(out)
    assert set(expect_tools) <= set(used), f"{q} 期望调用 {expect_tools}，实际 {used}"
```

**迁移收益**：
- 依赖从 40+ 个包降到 2 个（mcp + httpx）
- 启动时间从 3 秒降到 0.2 秒
- 可调试性大幅提升（30 行代码，一眼看完）
- 换模型只改 `llm_client` 一处

**迁移成本**：2～5 人日（视工具数量）。

## 9.6 什么情况下不要迁移

迁移不是免费的。以下情况**不要迁**：

| 情况 | 建议 |
| --- | --- |
| 系统稳定运行，无新需求 | 不迁。稳定压倒一切 |
| 团队不熟悉目标方案 | 先小范围试点，不要全量迁 |
| 没有测试覆盖 | 先补测试，再迁移（否则你不知道有没有迁坏） |
| 迁移收益 < 3 人日/年 | 不迁。算不过账 |
| 临近大促/关键节点 | 不迁。永远不要在关键期动架构 |

**判断公式**：

```text
迁移价值 = (年节省维护成本 + 年节省的故障损失) / 迁移人日
若 < 1，不迁；1~3，谨慎；> 3，值得迁
```

## 9.7 三年学习路线：从「会用」到「会选」

### 第 1 阶段（0～3 个月）：建立体感

**目标**：能独立搭出一个能用的 AI 应用。

| 内容 | 产出 |
| --- | --- |
| Python 基础 + HTTP + JSON | 能读懂 API 文档 |
| OpenAI 兼容 API 调用 | 能写一个命令行问答工具 |
| 提示词工程（CRAFT） | 能稳定拿到结构化输出 |
| 一个低代码平台（Dify） | 能搭一个文档问答机器人 |
| Git 基础 | 能管理自己的代码 |

**关键动作**：**不要看教程，直接做。** 选一个你自己真实的痛点，用 AI 做出来。

### 第 2 阶段（3～9 个月）：理解原理

**目标**：知道「为什么这样设计」，能判断方案好坏。

| 内容 | 产出 |
| --- | --- |
| Transformer 原理（读《Attention is All You Need》+ 图解） | 能解释 KV Cache 为什么省算力 |
| RAG 全链路（切片、embedding、检索、重排、生成） | 能调优一个 RAG 系统的召回率 |
| Agent 循环 + Function Calling | 能裸写一个 Agent，不用框架 |
| MCP 协议 | 能写一个 MCP Server 给别人用 |
| vLLM 部署 + 压测 | 能算出「这个配置能扛多少并发」 |
| 评测方法 | 能建一个 50 条的回归评测集 |

**关键动作**：**每学一个概念，写一篇 500 字的解释。** 写不出来就是没懂。

### 第 3 阶段（9～24 个月）：工程化

**目标**：能负责一个 AI 系统的从 0 到 1，并对线上负责。

| 内容 | 产出 |
| --- | --- |
| 网关（LiteLLM）+ 鉴权限流预算 | 能设计一个多租户 AI 平台 |
| 可观测性（trace、指标、日志） | 能在 10 分钟内定位线上问题 |
| 安全（提示注入、权限、沙箱） | 能通过一次安全评审 |
| 成本优化 | 能把单次请求成本降 50% |
| 团队协作（code review、文档、排期） | 能带一个小项目 |

**关键动作**：**主动接一个「有真实用户、会出事故」的项目。** 只有出过事故，才算真的会。

### 第 4 阶段（24 个月+）：判断力

**目标**：能在信息不全时做出正确决策。

这时候技术细节已经不是瓶颈，瓶颈是：
- 判断什么值得做（业务理解）
- 判断什么会失败（风险嗅觉）
- 判断人（团队组建）
- 判断趋势（技术品味）

**这一阶段没有教程，只能靠「做过足够多的决策并承担后果」积累。**

## 9.8 给「进公司」的实操建议

### 面试会问什么（AI 应用岗）

```text
基础层：
- 解释一下 KV Cache 是什么，为什么能加速
- temperature 和 top_p 的区别，什么时候用哪个
- 什么是 embedding，为什么能做语义检索

工程层：
- RAG 召回率低，你会怎么排查（至少说 5 个方向）
- Agent 老是循环调用同一个工具，怎么解决
- 怎么防止提示注入
- 你怎么评估一个 AI 应用「好不好」

架构层：
- 设计一个支持 1000 QPS 的 AI 客服系统
- 多租户怎么隔离
- 怎么控制成本
- 模型要换，怎么做到业务无感
```

**答题要点**：**先说结论，再说理由，最后说边界。** 不要背概念，讲你真实做过的。

### 入职前 30 天做什么

```text
第 1 周：读代码，画架构图。搞清楚「请求从哪来到哪去」。
第 2 周：跑通本地环境，改一个小 bug，走完整个发布流程。
第 3 周：读监控和日志，看最近三个月的故障记录。
第 4 周：找一个「小而确定」的改进点，做出来，让人看到。
```

**最重要的一件事**：**搞清楚「谁是决策者，他关心什么」**。技术方案再好，不解决他的问题就是白做。

### 不要做的事

- 不要一上来就提「重构」（你不知道历史包袱）
- 不要引入新框架（除非你能说清为什么现有的不行）
- 不要只跟代码打交道（AI 项目 80% 的问题在数据和业务）
- 不要承诺你验证不了的性能数字

| 术语 | 一句话解释 |
| --- | --- |
| Token | 模型处理文本的最小单位，中文约 1 字 ≈ 1～2 token |

| TPOT | Time Per Output Token，每字生成时间 |
| PagedAttention | vLLM 的核心技术，像操作系统分页一样管理 KV Cache |
| 连续批处理 | 请求动态进出批次，提高 GPU 利用率 |
| 前缀缓存 | 相同前缀复用 KV Cache，大幅降 TTFT |
| Embedding | 把文本变成向量，用于语义检索 |
| Rerank | 对初筛结果精排，提升相关性 |
| RAG | 检索增强生成，先查资料再回答 |
| Function Calling | 模型输出结构化调用请求，由程序执行 |
| Agent | 能自主决策、调用工具、多轮执行的程序 |
| ReAct | Reason + Act，边想边做的范式 |
| MCP | Model Context Protocol，模型与工具/数据的标准协议 |
| A2A | Agent to Agent，Agent 间通信协议 |
| 提示注入 | 攻击者在输入里藏指令，劫持模型行为 |
| 护栏 Guardrail | 对输入输出做校验和拦截的机制 |
| 人在回路 HITL | 关键步骤需人工确认 |
| 语义缓存 | 相似问题复用答案 |

# 附录 E：故障速查表

| 现象 | 最可能原因 | 第一步 |
| --- | --- | --- |
| 401 | Key 错/过期/没带 | 检查 Authorization 头 |
| 403 | 权限不足/额度用尽 | 查 key 的 model 白名单和预算 |
| 404 | URL 少 `/v1` 或模型名错 | 核对 base_url 和 model |
| 400 | 参数不支持/格式错 | 看 error.message，用 `drop_params` |
| 429 | 限流 | 查 RPM/TPM，加退避重试 |
| 500 | 上游故障 | 重试 + 切备用模型 |
| 首字极慢 | 上下文太长/无前缀缓存 | 砍上下文、开 prefix caching |
| 出字卡顿 | 显存不足/并发过高 | 看 GPU 利用率，降 max-num-seqs |
| 回答截断 | max_tokens 限制 | 调大，注意输入+输出总和 |
| 答非所问 | 检索塞了无关内容 | 打印真实 prompt 看 |
| 工具不触发 | 描述不清/模型不支持 | 改描述，换支持 FC 的模型 |
| 工具反复调用 | 无终止条件 | 设 max_steps，结果里加提示 |
| 输出格式错 | 无 schema 约束 | 加 response_format + 校验重试 |
| 成本暴涨 | Key 泄露/上下文膨胀/重试风暴 | 查花费曲线，吊销可疑 key |
| 质量下降但代码没改 | 模型升级/知识库更新 | 锁版本，跑评测集 |
| CUDA OOM | 显存不足 | 降上下文/量化/加卡 |
| 容器看不到 GPU | 没装 toolkit | `--gpus all` + 检查 nvidia-smi |

# 附录 F：成本估算公式

```text
单次请求成本 = 输入 token × 输入单价 + 输出 token × 输出单价

月成本 = 日请求数 × 30 × 单次成本 × (1 + 重试率)

自建月成本 = 硬件折旧 + 电费 + 运维人力 + 带宽
  硬件折旧 = 采购价 / 36（月）
  电费 = 功率(kW) × 24 × 30 × 电价

自建 vs 云 临界点：
  日请求数 × 30 × 单次成本 = 自建月成本
  → 日请求数 = 自建月成本 / (30 × 单次成本)

例：自建 4341 元/月，单次 0.008 元
    临界点 = 4341 / (30 × 0.008) ≈ 18000 次/日
```

**注意**：这个公式只算钱。如果算上「数据合规」「响应延迟」「可用性」，结论会变。**永远不要只按成本做决策。**

# 全书完

## 怎么用这本书

这本书不是读完就完的。建议这样用：

**第一遍（3 天）**：通读，不求甚解。目的是建立「地图」——知道什么问题该翻哪一章。

**第二遍（2 周）**：按你手头的真实项目，精读对应章节。每读一节，动手做一次。

**第三遍（长期）**：当手册用。遇到问题查目录，查附录 E 故障表。

## 三条最重要的提醒

1. **原理比框架重要**。框架三年一换，原理十年不变。第 1 章值得反复读。
2. **能跑起来比懂原理更优先**。先做出一个能用的东西，再回头补原理。顺序反了会卡死在半路。
3. **AI 是放大器，不是替代品**。它放大你的判断力，也放大你的错误。判断力只能自己长。

## 如果只记住一句话

> **把易变的东西做薄，把不变的东西做厚；把决策留给自己，把执行交给 AI。**
