## 2.2 调用形态：三种，本质只有一种

无论哪家，模型服务的调用形态只有三种，而且正在快速收敛到第二种。

**形态一：原生 SDK。** 厂商自己的协议，功能最全，但换厂商要改代码。

**形态二：OpenAI 兼容协议（事实标准）。** 绝大多数厂商和所有推理引擎都实现了 `POST /v1/chat/completions`。这意味着你可以用同一套代码，只改 `base_url` 和 `model` 就切换模型。**这是当下最重要的一个工程事实**，也是网关能存在的前提。

```python
from openai import OpenAI

client = OpenAI(api_key="sk-xxx", base_url="https://api.deepseek.com/v1")
resp = client.chat.completions.create(
    model="deepseek-chat",
    messages=[{"role": "user", "content": "用三句话解释什么是 KV Cache"}],
    temperature=0.3,
)
print(resp.choices[0].message.content)
```

换成 vLLM 本地部署，只改两行：

```python
client = OpenAI(api_key="EMPTY", base_url="http://127.0.0.1:8000/v1")
resp = client.chat.completions.create(model="Qwen/Qwen2.5-7B-Instruct", ...)
```

**形态三：自建 HTTP 封装。** 内部平台把模型能力包成自己的接口，统一鉴权、计费、审计。企业里最终都会走到这一步。

## 2.3 模型能力的四个关键分水岭

选模型时不要看榜单总分，看这四个能力，它们直接决定你的架构能不能成立：

| 能力 | 判断方法 | 不够会怎样 |
| --- | --- | --- |
| 指令遵循 | 给 10 条格式约束，看遵守几条 | 输出格式崩，解析失败 |
| 工具调用 | 给 5 个工具，看选对率 | Agent 走错路，或根本不调工具 |
| 长上下文有效利用 | 塞 5 万字后问中间细节 | 号称 128K，实际 8K 后就瞎 |
| 结构化输出 | 要求严格 JSON，看合法率 | 每次都要重试，成本翻倍 |

**一条经验：模型参数量与「多步规划能力」强相关。** 7B 模型能做好「单次工具调用 + 格式化输出」，但做不了 10 步以上的业务流程规划。如果你的业务需要长链推理，要么用 70B 以上 / 强推理模型，要么把长链拆成多个确定性步骤（工作流），让模型只做单步判断。这是架构层面的取舍，不是调参能解决的。

## 2.4 推理引擎深入：从权重到服务的最后一公里

### 量化：用精度换显存

| 精度 | 每参数字节 | 7B 模型显存 | 质量损失 | 适用 |
| --- | --- | --- | --- | --- |
| FP32 | 4 | ~28 GB | 无 | 训练 |
| FP16 / BF16 | 2 | ~14 GB | 极小 | 生产默认 |
| INT8 / FP8 | 1 | ~7 GB | 很小 | 高并发生产 |
| INT4 (AWQ/GPTQ) | 0.5 | ~4 GB | 可感知 | 消费级显卡、端侧 |
| 1.58bit (BitNet 类) | 0.2 | ~2 GB | 明显 | 实验性、极致端侧 |

记住一个粗算公式：

```text
显存需求 ≈ 参数量(B) × 每参数字节 × 1.2（框架开销） + KV Cache + 预留
```

例：Qwen2.5-7B 用 FP16 部署，7 × 2 × 1.2 ≈ 17 GB 权重，加 KV Cache 和上下文，**24 GB 显卡（4090 / A10）刚好够单人用，并发就爆**。要 10 并发 8K 上下文，至少 48 GB（A6000 / L40S）。

### 张量并行与多卡

单卡放不下时，把一层拆到多张卡上算（TP，Tensor Parallel）。经验：**TP 度数不超过单机 GPU 数，且优先 2/4/8 的 2 的幂**，因为跨卡通信开销随 TP 增大而上升。跨机部署（流水线并行 PP）延迟高，一般只在超大模型时用。

### 部署形态对比

| 形态 | 启动成本 | 并发 | 适用 |
| --- | --- | --- | --- |
| Ollama | 一条命令 | 低（默认串行） | 个人开发、演示、离线试用 |
| llama.cpp server | 编译后一条命令 | 中低，CPU 可跑 | 端侧、Mac、无 GPU 服务器 |
| vLLM | 一条命令 + 参数 | 高 | 生产 API 服务 |
| SGLang | 一条命令 | 很高 | 大规模、结构化输出密集 |
| TGI | Docker | 高 | HF 生态 |
| 云托管（Bedrock/百炼/火山） | 控制台点几下 | 弹性 | 不想运维 |

### 一个最小可用的 vLLM 启动命令

```bash
python -m vllm.entrypoints.openai.api_server \
  --model Qwen/Qwen2.5-7B-Instruct \
  --served-model-name qwen7b \
  --dtype bfloat16 \
  --max-model-len 16384 \
  --gpu-memory-utilization 0.90 \
  --max-num-seqs 32 \
  --enable-prefix-caching \
  --api-key sk-local-123 \
  --port 8000
```

关键参数解释：

- `--max-model-len`：单请求最大上下文。**开太大直接吃掉显存，是新手最常见的 OOM 原因。**
- `--gpu-memory-utilization`：允许 vLLM 占用显存比例，0.9 是常用值；和别的进程共卡时要调低。
- `--max-num-seqs`：同时处理的序列数，直接决定并发上限与延迟。
- `--enable-prefix-caching`：开启前缀缓存，系统提示词长的场景必开。
- `--api-key`：**本地也要设**，否则内网任何人都能白嫖你的卡。

## 2.5 模型选型的决策树

```text
数据能不能出内网？
├─ 不能（金融/政企/医疗/军工）
│   └─ 自部署开源模型
│       ├─ 有 GPU 集群 → vLLM + Qwen2.5-72B / DeepSeek-V3 量化版
│       ├─ 只有消费级卡 → vLLM + Qwen2.5-14B（INT4/AWQ）
│       └─ 只有 CPU / 端侧 → llama.cpp + Qwen2.5-7B INT4
└─ 能（多数互联网业务）
    ├─ 成本敏感、中文为主 → DeepSeek / Qwen API
    ├─ 长文档、代码、高指令遵循 → Claude / GPT
    ├─ 多模态 → Gemini / Qwen-VL
    └─ 要求国内合规发票 → 阿里百炼 / 火山 / 腾讯云
```

### 成本估算：一定要先算再做

```text
单次请求成本 = (输入 token × 输入单价 + 输出 token × 输出单价) / 1,000,000
月成本     = 单次成本 × 日均请求数 × 30 × (1 + 重试率)
```

举例：一个 RAG 客服，系统提示 + 检索内容 3000 token，输出 300 token，日请求 5000 次。

```text
按某国产模型 输入 2 元/百万、输出 8 元/百万：
单次 = (3000×2 + 300×8)/1e6 = 0.0084 元
月   = 0.0084 × 5000 × 30 ≈ 1260 元/月
```

如果换成旗舰模型（输入 20 元、输出 60 元），同样的量变成约 **1.1 万元/月**，差 9 倍。**这就是「路由」存在的商业理由**：简单问题走便宜模型，难问题走贵模型。第六章的网关就是干这个的。

## 2.6 模型层的六个真实坑

1. **上下文长度虚标**：标称 128K，实际超过 32K 后质量断崖。上线前必须做「长上下文压力测试」：把关键信息放在 10%、50%、90% 位置各测一遍。
2. **JSON 输出不稳定**：再强的模型也会偶发输出非法 JSON。生产必须做 schema 校验 + 自动重试 + 降级兜底，别信「它保证输出 JSON」。
3. **流式与工具调用冲突**：部分厂商在流式模式下 tool_call 分片返回，解析不当会丢参数。要么用官方 SDK，要么自己处理增量拼接。
4. **并发限流**：厂商 API 有 RPM/TPM 限制，超了直接 429。生产必须有队列 + 指数退避 + 多 key 轮询。
5. **版本漂移**：厂商会静默升级模型（`gpt-4o` 指向新快照），行为会变。**必须锁定具体版本号**，并在网关层做灰度。
6. **价格与条款变更**：模型价格一年能变好几次。把模型名、单价写进配置中心，不要硬编码在代码里。
